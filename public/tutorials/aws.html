Shared Responsibility Model

AWS Responsibility — Security OF the cloud Physical hardware, data centers, global network, managed service internals Hypervisor, host OS for managed services Customer Responsibility — Security IN the cloud Your data encryption, OS patching (EC2), IAM configuration Network controls (Security Groups, NACLs), application security
Exam/Interview Tip
The shared responsibility boundary shifts based on service type. For Lambda (serverless), AWS manages more (runtime, OS). For EC2, you manage the OS and above. Know where the line is for each service type.

IAM — Identity & Access Management

IAM is the cornerstone of AWS security — controlling who can do what on which resources. Every senior AWS interview includes IAM questions.

Core IAM Concepts

ConceptDescription
UserA person or app with long-lived credentials (avoid for services)
GroupCollection of users — attach policies to groups, not individual users
RoleAssumable identity — for services, cross-account, federated users
PolicyJSON document defining permissions (Allow/Deny on Actions/Resources)
Permission BoundaryMaximum permissions an entity can have — even if policy allows more

IAM Policy Anatomy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ReadWrite",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringEquals": { "aws:RequestedRegion": "us-east-1" }
      }
    },
    {
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "*"
    }
  ]
}

Policy Evaluation Logic

Request → Check for explicit DENY → If found: DENY immediately → Check for explicit ALLOW → If found: ALLOW → Default: DENY (implicit deny) Priority: Explicit Deny > Allow > Implicit Deny SCP (Org) > Resource Policy > IAM Policy > Permission Boundary > Session Policy

IAM Best Practices

# ✅ Use roles for EC2/Lambda — never embed credentials in code
aws iam create-role --role-name MyLambdaRole \
  --assume-role-policy-document file://trust-policy.json

# ✅ Least privilege — start with no permissions, add only what's needed
# ✅ Enable MFA for console access and critical operations
# ✅ Use AWS Organizations SCPs to enforce guardrails across accounts
# ✅ Rotate access keys; prefer short-lived role credentials
# ✅ Use Secrets Manager / SSM Parameter Store for credentials
# ❌ Never use root account for daily operations
# ❌ Never hardcode access keys in application code

Q: An EC2 application needs to read from DynamoDB. What is the correct approach?

A) Store AWS access keys as environment variables on the EC2 instance
B) Create an IAM user with DynamoDB permissions and embed the keys in code
C) Attach an IAM Role with a DynamoDB policy to the EC2 instance — credentials are auto-rotated via instance metadata
D) Use the root account credentials stored in Secrets Manager
✓ Correct! IAM Roles attached to EC2 deliver short-lived credentials via the instance metadata service (IMDS) — no keys in code, auto-rotation, no credential leakage risk.

Lambda Cold Start Deep Dive

Cold Start (new execution environment): Download package → Init runtime → Run init code → Handle request ↑_______________100ms – 1s overhead_______________↑ Warm invocation (reused environment): Handle request only ← milliseconds Provisioned Concurrency: pre-warmed environments, zero cold start
# Cold start mitigations

# 1. Move heavy init outside the handler (module-level)
const db = new Pool({ ... });          // created once per execution env
const client = new DynamoDBClient();   // reused on warm calls

exports.handler = async (event) => {
    return await db.query('SELECT ...');
};

# 2. Provisioned Concurrency (AWS CLI)
aws lambda put-provisioned-concurrency-config \
  --function-name my-fn \
  --qualifier LIVE \
  --provisioned-concurrent-executions 10

# 3. Lambda SnapStart (Java) — snapshots post-init state
# 4. Keep deployment package small — use layers for large deps
# 5. Choose Node.js/Python over Java/.NET for faster init

VPC & Networking

A VPC is your private network inside AWS. Understanding subnets, route tables, security groups, NACLs, and VPC connectivity is essential for any AWS architect role.

VPC Architecture

VPC 10.0.0.0/16 (region-wide) ├── Public Subnet 10.0.1.0/24 (AZ-a) │ Route: 0.0.0.0/0 → Internet Gateway │ Resources: ALB, NAT Gateway, Bastion ├── Private Subnet 10.0.2.0/24 (AZ-a) │ Route: 0.0.0.0/0 → NAT Gateway (outbound only) │ Resources: EC2, ECS, RDS, Lambda └── Isolated Subnet 10.0.3.0/24 (AZ-a) No internet route at all Resources: RDS, ElastiCache (DB tier)

Security Groups vs NACLs

Security GroupsNACLs
LevelInstance/ENI levelSubnet level
Stateful?✅ Yes — return traffic auto-allowed❌ No — must explicitly allow inbound AND outbound
RulesAllow onlyAllow and Deny
EvaluationAll rules evaluatedRules evaluated in number order, first match wins
DefaultDeny all inbound, allow all outboundAllow all (default NACL)

VPC Connectivity Options

# VPC Peering — direct, point-to-point, NOT transitive
# A↔B and B↔C does NOT mean A↔C
aws ec2 create-vpc-peering-connection \
  --vpc-id vpc-111 --peer-vpc-id vpc-222

# Transit Gateway — hub-and-spoke, fully transitive
# Scales to thousands of VPCs + on-premises connections
aws ec2 create-transit-gateway

# VPC Endpoints — private access to AWS services (no internet)
# Gateway endpoint: S3, DynamoDB (free)
# Interface endpoint: most other services (PrivateLink, $$$)
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-111 \
  --service-name com.amazonaws.us-east-1.s3 \
  --vpc-endpoint-type Gateway
VPC Peering Gotcha
VPC peering is NOT transitive. If VPC-A peers with VPC-B and VPC-B peers with VPC-C, traffic from A cannot reach C through B. Use Transit Gateway for hub-and-spoke connectivity at scale.

Q: You have 50 VPCs needing full mesh connectivity and on-premises access. What is the right approach?

A) Create VPC peering between all pairs (50×49/2 = 1,225 peerings)
B) Use a shared VPC with security group isolation
C) Use Transit Gateway — attach all VPCs and on-premises Direct Connect/VPN for centralized transitive routing
D) Assign Elastic IPs and route over the internet
✓ Correct! Transit Gateway is the hub-and-spoke solution for large-scale VPC connectivity. It supports transitive routing, on-premises connectivity, and inter-region peering.

Dead Letter Queues (DLQ)

# DLQ — messages that fail after maxReceiveCount are moved here
# Without DLQ: poison-pill messages loop forever, blocking consumers

aws sqs create-queue --queue-name MyDLQ
aws sqs set-queue-attributes \
  --queue-url https://sqs.us-east-1.amazonaws.com/123/MyQueue \
  --attributes '{
    "RedrivePolicy": "{\"deadLetterTargetArn\":\"arn:aws:sqs:us-east-1:123:MyDLQ\",
                      \"maxReceiveCount\":\"3\"}"
  }'

# CloudWatch alarm on ApproximateNumberOfMessagesNotVisible in DLQ

Athena Cost Optimization

-- Athena charges $5/TB scanned — optimize to reduce costs

-- 1. Use columnar formats (Parquet/ORC) — 70-90% less data scanned
CREATE TABLE orders_parquet
WITH (format = 'PARQUET', external_location = 's3://bucket/orders/')
AS SELECT * FROM orders_csv;

-- 2. Partition your data
-- s3://bucket/orders/year=2024/month=01/day=15/
CREATE TABLE orders_partitioned (id STRING, total DOUBLE)
PARTITIONED BY (year STRING, month STRING);

-- 3. Use partition pruning in queries
SELECT * FROM orders_partitioned
WHERE year = '2024' AND month = '01';  -- Only scans Jan 2024 partition

CAP Theorem & Distributed Systems

CAP Theorem explains the fundamental trade-offs in distributed systems. Knowing where AWS services land on the CAP spectrum is a senior-level topic.

CAP Theorem

Consistency Every read returns the most recent write / \ CP CA / \ Availability ────── AP ────── Partition Tolerance Every request Network partitions ALWAYS happen gets a response → P is required for distributed systems Real choice: CP (consistency) or AP (availability) during a partition

AWS Services on the CAP Spectrum

ServiceDefault CAPTunable?Notes
DynamoDBAP (eventual)✅ Strongly consistent readsStrongly consistent = higher latency, costs 2x RCUs
AuroraCPNoQuorum writes to 6 copies across 3 AZs
S3CP (since 2020)NoStrong read-after-write consistency for all operations
ElastiCache RedisCP (primary)NoRead from replica = eventual consistency
KinesisCPNoOrdered within shard, at-least-once delivery

PACELC Extension

Beyond CAP: PACELC
PACELC extends CAP: during a Partition: A vs C trade-off. Else (normal operation): Latency vs Consistency. DynamoDB: PA/EL — available during partitions, low latency over consistency in normal operation. Aurora: PC/EC — consistent always.
// DynamoDB — choose read consistency per request
const result = await dynamodb.getItem({
  TableName: "Orders",
  Key: { id: { S: "order-123" } },
  // Eventually consistent (default) — cheaper, faster
  ConsistentRead: false,

  // Strongly consistent — use when reading after a write
  // ConsistentRead: true  ← 2x RCU cost, higher latency
});

A) Aurora — it uses synchronous replication
B) DynamoDB — eventually consistent reads by default, strong consistency optional
C) RDS Multi-AZ — the standby ensures consistency
D) S3 — object storage is always consistent
✓ Correct! DynamoDB is AP by default — eventual consistency for maximum availability. Strongly consistent reads are available at 2x the RCU cost.

Encryption & Key Management (KMS)

KMS is the heart of AWS encryption — understanding CMKs, data key encryption, envelope encryption, and key policies is essential for any security-focused role.

Envelope Encryption

KMS CMK (Customer Master Key — never leaves KMS) │ │ GenerateDataKey() — KMS creates a data key ▼ Data Key (plaintext + encrypted copy) │ ├── Encrypt your data with plaintext data key (AES-256) │ └── Store encrypted data key alongside ciphertext (throw away plaintext data key) Decrypt: Send encrypted data key to KMS → get plaintext data key back → decrypt data

KMS Key Types

TypeManagementCostUse Case
AWS Managed KeyAWS manages rotation, policyFreeDefault for S3, RDS, EBS
Customer Managed Key (CMK)You control policy, rotation$1/key/mo + $0.03/10k API callsCustom access control, cross-account, audit
AWS Owned KeyAWS (completely hidden)FreeInternal service use, no visibility

KMS Key Policy + Secrets Manager

# KMS Key Policy — who can use the key
{
  "Sid": "AllowLambdaDecrypt",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::123:role/MyLambdaRole" },
  "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
  "Resource": "*"
}

# Secrets Manager — store secrets encrypted with KMS CMK
# Auto-rotation with Lambda rotators
aws secretsmanager create-secret \
  --name "prod/db/password" \
  --kms-key-id "arn:aws:kms:us-east-1:123:key/KEY_ID" \
  --secret-string '{"username":"admin","password":"s3cr3t"}'

# Retrieve in Lambda (SDK handles decryption transparently)
const secret = await secretsmanager.getSecretValue({ SecretId: "prod/db/password" }).promise();
const creds = JSON.parse(secret.SecretString);
Never Do This
Never store secrets in environment variables as plaintext, hard-coded in Lambda/ECS, or committed to source control. Always use Secrets Manager or SSM Parameter Store (SecureString) with KMS encryption.

Q: In KMS envelope encryption, what is stored alongside the encrypted data?

A) The plaintext data key
B) The encrypted (wrapped) data key — which KMS can decrypt on demand
C) The CMK ARN only
D) A hash of the data key
✓ Correct! The encrypted (wrapped) data key is stored with the ciphertext. To decrypt, you send the wrapped key to KMS → get plaintext data key → decrypt data. The CMK never leaves KMS.

Event-Driven Architecture

Event-driven architecture decouples producers from consumers, enabling resilient, scalable systems. AWS provides a complete event-driven toolkit — knowing when to use each service is key.

Event-Driven Patterns on AWS

Domain Event (something happened) │ ├── EventBridge — rule-based routing to 50+ targets │ Best for: AWS service events, SaaS integrations, complex routing │ ├── SNS + SQS Fan-out — push to many queues │ Best for: Fan-out to multiple microservices │ ├── Kinesis Data Streams — ordered, replay-able stream │ Best for: High-volume real-time analytics, ordered events │ └── DynamoDB Streams — CDC from DynamoDB Best for: Reacting to database changes (trigger Lambda)

Saga Pattern for Distributed Transactions

// Choreography-based Saga (EventBridge)
// Each service publishes events, others react

// 1. Order Service → publishes "OrderCreated"
// 2. Payment Service → listens "OrderCreated" → publishes "PaymentProcessed" or "PaymentFailed"
// 3. Inventory Service → listens "PaymentProcessed" → publishes "InventoryReserved"
// 4. Shipping Service → listens "InventoryReserved" → publishes "ShipmentCreated"

// Compensation (rollback) on failure:
// PaymentFailed → Order Service listens → publishes "OrderCancelled"
// InventoryFailed → Payment Service listens → publishes "PaymentRefunded"

// Orchestration-based Saga (Step Functions)
// Central orchestrator controls the workflow
// Explicit compensation states in the state machine
// Better visibility, easier debugging

Idempotency — Critical for Event-Driven Systems

// SQS at-least-once: same message may arrive twice
// Lambda must be idempotent — handle duplicates safely

async function processOrder(event) {
  const { orderId } = event;

  // Check if already processed (DynamoDB conditional write)
  try {
    await dynamodb.put({
      TableName: 'ProcessedEvents',
      Item: { orderId, processedAt: new Date().toISOString() },
      ConditionExpression: 'attribute_not_exists(orderId)'  // reject duplicate
    }).promise();
  } catch (e) {
    if (e.code === 'ConditionalCheckFailedException') return;  // already processed
    throw e;
  }
  // process order...
}

Q: In a Saga pattern, what is a "compensation transaction"?

A) A transaction that consolidates billing across services
B) A reverse transaction that undoes a previously completed step when a later step fails
C) A read-only transaction that checks consistency
D) A transaction that retries a failed step automatically
✓ Correct! Compensation transactions are "undo" operations — e.g., if shipping fails, trigger a PaymentRefund and InventoryRelease to maintain data consistency without a distributed 2PC transaction.

Serverless Architecture Patterns

Serverless isn't just Lambda — it's a full architecture philosophy. Knowing when serverless fits, how to design it for scale, and its trade-offs is essential for architect-level interviews.

Full Serverless Stack

Frontend: S3 + CloudFront (static hosting, global CDN) ↓ API Layer: API Gateway HTTP API (throttling, auth) ↓ Auth: Cognito User Pools + JWT authorizer ↓ Compute: Lambda functions (per endpoint) ↓ Data: DynamoDB (on-demand) + S3 (objects) + ElastiCache (sessions) ↓ Async: SQS → Lambda (background jobs) ↓ Observability: CloudWatch + X-Ray + Lambda Powertools

Lambda Powertools

from aws_lambda_powertools import Logger, Tracer, Metrics
from aws_lambda_powertools.metrics import MetricUnit

logger = Logger()         # structured JSON logging + correlation IDs
tracer = Tracer()         # X-Ray tracing with cold start annotations
metrics = Metrics(namespace="MyApp")

@logger.inject_lambda_context
@tracer.capture_lambda_handler
@metrics.log_metrics
def handler(event, context):
    logger.info("Processing order", extra={"order_id": event["orderId"]})
    metrics.add_metric(name="OrdersProcessed", unit=MetricUnit.Count, value=1)

    with tracer.provider.in_subsegment("##payment"):
        result = process_payment(event)

    return {"statusCode": 200, "body": json.dumps(result)}

Top AWS Anti-patterns

Anti-patternProblemFix
Binding to 0.0.0.0Services exposed on all network interfacesBind to localhost/specific IPs; use Security Groups
Hardcoded credentialsKeys committed to code/configIAM Roles + Secrets Manager
Single-AZ architectureOne AZ failure = full outageAlways deploy Multi-AZ with ALB
