Getting Started

What is GraphQL? Interview Q1

GraphQL is a query language for APIs and a runtime for executing those queries. It was created by Facebook in 2012 and open-sourced in 2015. It solves fundamental problems with REST.

The problems GraphQL solves

RESTGraphQL
EndpointsMany (one per resource)Single /graphql
Data shapeFixed by serverDefined by client
Over-fetchingCommon — extra fields returnedEliminated — ask for exactly what you need
Under-fetchingMultiple round-trips for related dataOne query fetches everything
Type systemOptional (OpenAPI)Built-in, strongly typed
VersioningURL or headers (/v2/)Additive schema evolution

A concrete example

# REST: need 3 separate API calls
# GET /users/1
# GET /users/1/posts
# GET /posts/42/comments

# GraphQL: one query, exactly the data you want
query {
  user(id: "1") {
    name
    email
    posts {
      title
      comments {
        body
        author { name }
      }
    }
  }
}

Key trade-offs to know for interviews

  • HTTP caching is harder — all queries are POSTs to one endpoint (use Persisted Queries to enable GETs)
  • N+1 problem — naive resolver implementations cause database query explosions (use DataLoader)
  • Schema design upfront — more investment than REST but pays off with type safety
  • Observability — you need operation-level metrics, not just endpoint-level

🧠 Quick Check — What does "over-fetching" mean in the context of REST APIs?

Making too many API calls in a short time
The server returns more fields than the client actually needs, wasting bandwidth
Fetching data that is already cached

Schema & Types

The schema is the contract between the client and server. It defines every type, field, and operation available in your API.

SDL — Schema Definition Language

# Scalar types: String, Int, Float, Boolean, ID
# ! means non-nullable (required)

type User {
  id:        ID!
  name:      String!
  email:     String!
  age:       Int           # nullable — can be null
  posts:     [Post!]!      # non-null list of non-null Posts
}

type Post {
  id:        ID!
  title:     String!
  author:    User!
  published: Boolean!
}

# Entry points — root types
type Query {
  user(id: ID!): User
  posts: [Post!]!
}

type Mutation {
  createPost(input: CreatePostInput!): Post!
}

# Input types — for mutation arguments
input CreatePostInput {
  title:    String!
  authorId: ID!
}

Enums, Unions, and Interfaces

# Enum — restricted set of values
enum Role { ADMIN  USER  MODERATOR }

# Interface — shared fields across types
interface Node { id: ID! }
type Article implements Node { id: ID!  title: String! }

# Union — one of several types (no shared fields)
union SearchResult = User | Post | Article

# Query using inline fragments to handle union types
query {
  search(text: "GraphQL") {
    ... on User    { name email }
    ... on Post    { title }
    ... on Article { title }
  }
}

🧠 Quick Check — What does ! mean on a field type like name: String!?

The field is non-nullable — the server guarantees it will never return null
The field is required in input arguments only
The field must be unique across all objects

Queries, Mutations & Subscriptions Interview Q3

GraphQL has three operation types. Each has different semantics — knowing them cold is table-stakes for any GraphQL interview.

Query — read data (runs in parallel)

type Query {
  user(id: ID!): User
  posts(limit: Int = 10): [Post!]!
}

# Client query with variables — no string interpolation!
query GetUser($id: ID!) {
  user(id: $id) {
    name
    email
    posts { title }
  }
}
# Variables sent separately: { "id": "123" }

Mutation — write data (runs serially)

type Mutation {
  createPost(input: CreatePostInput!): Post!
  deletePost(id: ID!): Boolean!
}

mutation NewPost($input: CreatePostInput!) {
  createPost(input: $input) { id title }
}
# Multiple mutations in one request execute SERIALLY to avoid race conditions
# Multiple queries execute in PARALLEL

Subscription — real-time push (WebSocket)

type Subscription {
  messageAdded(channelId: ID!): Message!
}

subscription OnMessage($channelId: ID!) {
  messageAdded(channelId: $channelId) { id body author { name } }
}
# Server uses Pub/Sub (Redis) to push events via persistent WebSocket

🧠 Quick Check — You send one request with 3 mutations. In what order do they execute?

In parallel — same as queries
Serially — one at a time, in the order they appear, to prevent race conditions
Order depends on the server implementation

Resolvers & The Execution Engine Interview Q8 & Q9

Resolvers are the functions that power each field. GraphQL walks your query tree calling resolvers top-down.

Resolver signature: (parent, args, context, info)

const resolvers = {
  Query: {
    user: (parent, args, context, info) => {
      // parent  — resolved value of the parent field (null for root Query)
      // args    — { id: "123" }
      // context — { currentUser, db, loaders }
      // info    — AST field info, path, schema
      return context.db.findUser(args.id);
    }
  },
  User: {
    posts: (user, args, context) => context.db.findPostsByUser(user.id)
  }
};

How GraphQL walks the query tree

query { user(id:"1") { name posts { title } } } 1. Query.user → returns { id:"1", name:"Alice" } 2. User.name → default resolver returns "Alice" 2. User.posts → resolver returns [{ id:5, title:"Hello" }] 3. Post.title → default resolver returns "Hello" Default resolver: (parent) => parent[fieldName] — no code needed!

Custom scalars Interview Q9

const { GraphQLScalarType, Kind } = require('graphql');

const DateScalar = new GraphQLScalarType({
  name: 'Date',
  serialize:    (v) => v.toISOString(),          // outgoing: Date → String
  parseValue:   (v) => new Date(v),              // from variables
  parseLiteral: (ast) => ast.kind === Kind.STRING  // from inline literal
    ? new Date(ast.value) : null,
});
// Use in schema: scalar Date    createdAt: Date!

🧠 Quick Check — What is the parent argument in a resolver?

The HTTP request object
The resolved value returned by the parent field's resolver — passed down to every child field resolver
The GraphQL schema parent type definition

Subscriptions at Scale Interview Q11

Subscriptions enable real-time server-to-client push. Single-server in-memory PubSub is easy; scaling it across instances requires a shared backend like Redis.

Basic setup

const { PubSub } = require('graphql-subscriptions');
const pubsub = new PubSub(); // in-memory — single server only!

const resolvers = {
  Mutation: {
    sendMessage: async (_, { channelId, body }, { db }) => {
      const msg = await db.createMessage({ channelId, body });
      pubsub.publish(`MSG_${channelId}`, { messageAdded: msg });
      return msg;
    }
  },
  Subscription: {
    messageAdded: {
      subscribe: (_, { channelId }) => pubsub.asyncIterator(`MSG_${channelId}`)
    }
  }
};

Horizontal scaling with Redis PubSub

Client A ─WS─▶ Server 1 ─subscribe─▶ Redis Client B ─WS─▶ Server 2 ─publish──▶ Redis ──▶ Server 1 ──▶ Client A Any server publishes; Redis fans out to ALL subscribed server instances.
const { RedisPubSub } = require('graphql-redis-subscriptions');
const pubsub = new RedisPubSub({
  publisher:  new Redis({ host: process.env.REDIS_HOST }),
  subscriber: new Redis({ host: process.env.REDIS_HOST }),
});
// Swap the pubsub variable — all resolver code stays identical

🧠 Quick Check — Why doesn't in-memory PubSub work with multiple server instances?

WebSockets require a shared memory space
The event bus is isolated per process — a client on Server 1 won't receive events published on Server 2
Redis is always faster, so it's preferred

Fragments Interview Q5

Fragments are reusable field selections. They keep queries DRY and are the building block of component-driven GraphQL clients.

Named fragments — reuse field selections

fragment UserCard on User {
  id
  name
  avatarUrl
}

query GetPosts {
  posts { title  author { ...UserCard } }  # spread fragment
}

query GetComments {
  comments { body  author { ...UserCard } }  # reused
}

Inline fragments — for unions and interfaces

query Search($text: String!) {
  search(text: $text) {
    # Inline fragments — conditionally select fields per concrete type
    ... on Book   { title pageCount }
    ... on Movie  { title duration }
    ... on Author { name bookCount }
    __typename  # always available — tells you which type was returned
  }
}

🧠 Quick Check — When do you NEED an inline fragment?

When a fragment has more than 5 fields
When a field returns a union or interface type and you need to select fields specific to each concrete type
When the query is a mutation

Auth & Context Interview Q4

GraphQL has no built-in auth. The standard pattern: validate JWT in context, check permissions in resolvers or directives.

Authentication via context builder

const server = new ApolloServer({ typeDefs, resolvers });

// Runs once per request — before any resolver
const context = ({ req }) => {
  const token = req.headers.authorization?.split(' ')[1];
  try {
    const user = token ? verifyJWT(token) : null;
    return { user, db, loaders: createLoaders(db) };
  } catch {
    return { user: null, db };
  }
};

Authorization approaches

// 1. Resolver-level (simple but scattered)
deletePost: (_, { id }, { user }) => {
  if (!user) throw new GraphQLError('Not authenticated', { extensions: { code: 'UNAUTHENTICATED' }});
  if (!user.isAdmin) throw new GraphQLError('Forbidden', { extensions: { code: 'FORBIDDEN' }});
  return db.deletePost(id);
}

// 2. Schema directive (declarative, clean)
type Mutation {
  deletePost(id: ID!): Boolean @auth(requires: ADMIN)
}

// 3. graphql-shield (separate permission layer — best for complex rules)
const permissions = shield({
  Mutation: { deletePost: and(isAuthenticated, isAdmin) }
});

🧠 Quick Check — Where should JWT validation happen in a GraphQL server?

Inside each resolver that needs authentication
In the context builder — once per request. All resolvers then read context.user.
In the schema type definitions

The N+1 Problem & DataLoader Interview Q2

The N+1 problem is the #1 GraphQL performance pitfall. DataLoader is the canonical fix — it batches and caches per-request.

The problem

// Query: posts { title author { name } }
// 1 query: SELECT * FROM posts  → 100 rows
// N queries: SELECT * FROM users WHERE id = 1
//            SELECT * FROM users WHERE id = 2
//            ... × 100 = 101 total DB queries!

The fix: DataLoader

const DataLoader = require('dataloader');

// Batch function: receives array of ALL keys collected in the same event loop tick
const userLoader = new DataLoader(async (userIds) => {
  const users = await db.findUsersByIds(userIds); // ONE query for ALL ids
  return userIds.map(id => users.find(u => u.id === id)); // preserve order!
});

// Resolver: .load() queues — doesn't fire immediately
Post: { author: (post) => userLoader.load(post.authorId) }
// Called 100x — but DataLoader fires ONE batch query

// IMPORTANT: create a new loader PER REQUEST (not global)
// Global loader = stale cache across requests = data leaks between users
const createLoaders = () => ({
  users: new DataLoader(ids => db.findUsersByIds(ids)),
});

🧠 Quick Check — What happens if you reuse the same DataLoader instance globally across all requests?

It runs out of memory faster
Results are cached globally — one user may receive stale or another user's cached data (data leak / security issue)
The batch function stops working after the first request

Apollo Federation Interview Q6

Federation lets multiple teams each own a subgraph. The Apollo Router composes them into one unified supergraph that clients query as a single API.

Schema stitching vs Federation

Schema StitchingApollo Federation
OwnershipGateway owns merge configEach subgraph declares its own schema
CompositionManual, at gatewayAutomatic (Rover CLI / Managed Federation)
Cross-service typesManual type merging@key directive — automatic entity resolution
Recommended?Legacy✅ Modern choice

Federation in action

// Users subgraph — owns User type
type User @key(fields: "id") {
  id:    ID!
  name:  String!
  email: String!
}

// Orders subgraph — extends User with orders
extend type User @key(fields: "id") {
  id:     ID! @external
  orders: [Order!]!
}
// Resolver in Orders subgraph:
// User: { orders: (user) => db.findOrdersByUserId(user.id) }
Client ──▶ Apollo Router (supergraph) │ ┌──────────┴──────────┐ ▼ ▼ Users subgraph Orders subgraph (owns User type) (extends User.orders)

🧠 Quick Check — What does @key(fields: "id") do in Apollo Federation?

It makes the field non-nullable
It designates the primary key for an entity, allowing the Apollo Router to stitch the type across subgraphs by resolving it from its owning subgraph
It creates an index on that field in the database

Persisted Queries Interview Q7

Automatic Persisted Queries (APQ) reduce payload size and unlock HTTP GET caching for GraphQL — two things REST has for free.

How APQ works

First request (cold miss): Client → { extensions: { persistedQuery: { sha256Hash: "abc123" } } } Server: hash not in cache → "PersistedQueryNotFound" Client → resends with full query + hash Server: executes + caches hash→query Subsequent requests (cache hit): Client → { extensions: { persistedQuery: { sha256Hash: "abc123" } } } Server: hash found → executes from cache = 64-char payload instead of full query string = Can use HTTP GET → CDN and browser caching works!
// Apollo Client — enable APQ
import { createPersistedQueryLink } from '@apollo/client/link/persisted-queries';
import { sha256 } from 'crypto-hash';

const link = createPersistedQueryLink({ sha256 }).concat(httpLink);
// That's all — the rest is automatic

// Server production mode: allowlist only registered queries
// Reject any ad-hoc queries — malicious queries can't run

🧠 Quick Check — APQ enables HTTP GET for GraphQL queries. Why is this valuable?

GET is processed faster by Node.js servers
GET requests are cacheable by CDNs and browsers — read queries become cacheable like REST GET endpoints
GET requests bypass authentication

Error Handling Interview Q10

GraphQL's partial success model is unique — a response can have both data and errors at the same time.

Partial success response

// Even when a resolver throws, HTTP status is still 200
{
  "data": {
    "post": {
      "title": "Hello",
      "author": null      // nullable field — resolver threw
    }
  },
  "errors": [{
    "message": "User not found",
    "path": ["post", "author"],
    "extensions": { "code": "NOT_FOUND" }
  }]
}

Null propagation rule

If a non-nullable (!) field resolver throws: → that field becomes null → null propagates UP to the nearest nullable ancestor → that ancestor becomes null too Risk: A single failing resolver in a deeply nested non-nullable tree can null out the entire response. Design schemas carefully!

Production error handling

const server = new ApolloServer({
  typeDefs, resolvers,
  formatError: (formattedErr) => {
    // Strip stack traces and internal details in production
    if (formattedErr.extensions?.code === 'INTERNAL_SERVER_ERROR') {
      logger.error(formattedErr);
      return { message: 'Internal server error', extensions: { code: 'INTERNAL_SERVER_ERROR' }};
    }
    return formattedErr;
  }
});

🧠 Quick Check — A nullable field's resolver throws an error. What is the HTTP response status code?

500 — because a resolver threw
200 — GraphQL returns data (partial, field is null) and errors array. HTTP layer stays 200.
404 — because the resource was not found

Security: Complexity & Depth Limiting Interview Q12

GraphQL's flexibility is a security risk. Without safeguards, a client can craft queries that DoS your server with a single request.

The attack: exponential query

# 100 friends per level × 5 depths = 10 billion potential DB lookups
{ friends { friends { friends { friends { friends { name } } } } } }

Depth limiting + Complexity limiting

const depthLimit = require('graphql-depth-limit');
const { createComplexityRule } = require('graphql-query-complexity');

const server = new ApolloServer({
  typeDefs, resolvers,
  validationRules: [
    depthLimit(7),              // reject queries > 7 levels deep
    createComplexityRule({
      maximumComplexity: 1000,  // total field-cost budget
      estimators: [simpleEstimator({ defaultComplexity: 1 })]
    })
  ]
});

Full production security checklist

ProtectionTool
Depth limitgraphql-depth-limit
Complexity limitgraphql-query-complexity
Rate limitingGateway / reverse proxy by IP or token
Query allowlistAPQ + server-side allowlist (production only)
Disable introspectionintrospection: process.env.NODE_ENV !== 'production'
Query timeoutMax execution time via plugin

🧠 Quick Check — Why disable introspection in production?

Introspection queries are very slow
It exposes your entire schema to attackers — they can discover field names, types, and craft targeted malicious queries
It breaks Apollo Client in production

Schema Evolution & Wrap-up Interview Q13

GraphQL APIs evolve without versions. The golden rule: only add fields — never remove or change existing ones without a proper deprecation cycle.

Breaking vs non-breaking changes

# ✅ Safe — additive changes only
type User {
  id:       ID!
  name:     String!
  username: String       # ✅ new nullable field
  fullName: String @deprecated(reason: "Use name")  # mark old
}

# ❌ Breaking — NEVER without migration:
# Remove a field       → clients that use it break
# Rename a field       → clients break
# Change String → Int  → type mismatch
# Add ! to nullable   → clients expecting null break

Detecting breaks in CI with graphql-inspector

# CLI — compare old vs new schema
# npx graphql-inspector diff old-schema.graphql new-schema.graphql
# ✖ Field 'User.email' was removed     ← Breaking! CI fails
# ✔ Field 'User.username' was added    ← Safe

# Apollo Studio: usage-aware schema checks
# rover graph check my-graph --schema ./schema.graphql
# Only blocks if clients are ACTIVELY using the removed field

🧠 Final Check — Which of these schema changes is a breaking change?

Adding a new nullable field username: String to a type
Changing an existing field from String to Int
Adding @deprecated to a field

Testing GraphQL APIs

Effective testing of a GraphQL API requires unit-testing resolvers, integration-testing the full schema, and contract-testing against consumers. Each layer catches different bugs.

Testing Pyramid for GraphQL

Contract / E2E — few; test full client-server round-trip /\ / \ Integration — test schema + resolver chain with real DB (or test container) / \ / \ Unit (resolver) — mock datasources; test business logic in isolation

Unit-testing a Resolver

// userResolver.test.ts
import { userResolver } from './userResolver';

const mockCtx = {
  dataSources: {
    userAPI: {
      getUser: jest.fn().mockResolvedValue({ id: '1', name: 'Alice' })
    }
  },
  user: { id: '1', role: 'user' }
};

test('Query.user returns user from datasource', async () => {
  const result = await userResolver.Query.user(null, { id: '1' }, mockCtx);
  expect(result).toEqual({ id: '1', name: 'Alice' });
  expect(mockCtx.dataSources.userAPI.getUser).toHaveBeenCalledWith('1');
});

Integration Test with graphql() Executor

import { graphql } from 'graphql';
import { schema } from './schema';

test('full query executes against in-memory schema', async () => {
  const { data, errors } = await graphql({
    schema,
    source: `query { user(id: "1") { id name } }`,
    contextValue: { dataSources: { userAPI: { getUser: async () => ({ id: '1', name: 'Alice' }) } } }
  });
  expect(errors).toBeUndefined();
  expect(data?.user).toMatchObject({ id: '1', name: 'Alice' });
});
Jest + graphql executor
The graphql() function executes a query against any schema in-process — no HTTP server needed. This makes integration tests extremely fast and eliminates network flakiness.

🧠 Which layer of the test pyramid should test that a resolver correctly calls its DataSource?

E2E / contract test
Unit test — mock the DataSource and assert the call was made with the right arguments
No test needed — DataSources are tested separately

Caching Strategies Interview Q14

GraphQL's flexible query shape breaks naive HTTP caching. Understanding the three caching layers — HTTP, CDN, and response-level — is essential for high-traffic APIs.

Three Caching Layers

LayerMechanismScope
HTTP (CDN)Automatic Persisted Queries (APQ) via GETPublic, per-query
Response cache@cacheControl directive + CDN headersPer-type / per-field
DataSource cacheIn-memory or Redis cache in DataSource layerPer-entity, server-side

Apollo Server @cacheControl

# schema — annotate types and fields with cache hints
type Product @cacheControl(maxAge: 300) {
  id:    ID!
  name:  String!
  price: Float!  @cacheControl(maxAge: 30)   # price changes more often
  owner: User     @cacheControl(scope: PRIVATE)  # never CDN-cache user data
}

// Apollo Server — enable cache control headers
const server = new ApolloServer({
  schema,
  plugins: [ApolloServerPluginCacheControl({ defaultMaxAge: 0 })]
});
// Response includes: Cache-Control: max-age=30, public

DataSource-level Redis Cache

class ProductAPI {
  async getProduct(id: string) {
    const key = `product:${id}`;
    const cached = await redis.get(key);
    if (cached) return JSON.parse(cached);
    const product = await db.findById(id);
    await redis.setEx(key, 300, JSON.stringify(product));
    return product;
  }
}
Private Data Warning
Any field marked PRIVATE scope (e.g., user email) must never be CDN-cached. Apollo sets Cache-Control: private for responses containing private-scoped fields — ensure your CDN respects this header.

🧠 Why does a standard CDN struggle to cache GraphQL POST requests?

CDNs don't support JSON
POST bodies are not cached by CDNs by default — all queries hit the same URL, so CDNs can't distinguish them. APQ + GET requests solve this by encoding the query in the URL.
GraphQL responses are always too large to cache

Pagination: Cursor vs Offset Interview Q16

GraphQL's Relay Connection spec is the industry standard for cursor-based pagination. Understanding its structure and the tradeoffs vs offset pagination is a senior-level expectation.

Relay Connection Spec

# Schema
type Query {
  users(first: Int, after: String, last: Int, before: String): UserConnection!
}

type UserConnection {
  edges:    [UserEdge!]!
  pageInfo: PageInfo!
}

type UserEdge {
  node:   User!
  cursor: String!   # opaque, base64-encoded position
}

type PageInfo {
  hasNextPage:     Boolean!
  hasPreviousPage: Boolean!
  startCursor:     String
  endCursor:       String
}

Resolver Implementation

// Query.users resolver
async function users(_, { first = 10, after }, ctx) {
  const afterId = after ? decodeCursor(after) : null;

  const rows = await ctx.db.query(`
    SELECT * FROM users
    WHERE ($1::int IS NULL OR id > $1)
    ORDER BY id ASC LIMIT $2
  `, [afterId, first + 1]);  // fetch +1 to detect hasNextPage

  const hasNextPage = rows.length > first;
  if (hasNextPage) rows.pop();

  return {
    edges: rows.map(r => ({ node: r, cursor: encodeCursor(r.id) })),
    pageInfo: {
      hasNextPage,
      hasPreviousPage: !!afterId,
      startCursor: rows[0] ? encodeCursor(rows[0].id) : null,
      endCursor:   rows[rows.length-1] ? encodeCursor(rows[rows.length-1].id) : null
    }
  };
}
ApproachProsCons
Cursor (Relay)Stable, O(log n) per page, handles insertsNo random-page access
OffsetRandom access, simple SQLO(n) DB scan, skips on live inserts

🧠 What does the cursor in a Relay connection represent?

The total count of items
An opaque, stable pointer to a specific position in the dataset — typically a base64-encoded primary key or composite key — used as a WHERE clause anchor for the next page query
The page number multiplied by page size

File Uploads

GraphQL wasn't designed for binary data, but the graphql-upload spec extends it with multipart form data. Know both the standard approach and why REST/presigned URLs are often better.

graphql-upload Pattern

# Schema — scalar Upload is provided by graphql-upload
scalar Upload

type Mutation {
  uploadAvatar(file: Upload!): UploadResult!
}

// Resolver
async function uploadAvatar(_, { file }, ctx) {
  const { createReadStream, filename, mimetype } = await file;

  // Validate mime type before storing
  const allowed = ['image/jpeg', 'image/png', 'image/webp'];
  if (!allowed.includes(mimetype))
    throw new GraphQLError('Invalid file type', { extensions: { code: 'BAD_USER_INPUT' } });

  const stream = createReadStream();
  const url = await ctx.storage.upload({ stream, filename });
  return { url };
}

Presigned URL Pattern (Recommended)

# Better: GraphQL just generates a presigned URL; client uploads directly to S3/GCS
type Mutation {
  createUploadUrl(filename: String!, contentType: String!): PresignedUpload!
}

type PresignedUpload {
  uploadUrl: String!   # PUT to this URL directly from browser
  fileKey:   String!   # use this key in subsequent mutations
}

// Advantages: no binary data in GraphQL server, direct S3 transfer,
// no memory pressure, built-in CDN caching
Presigned URLs vs graphql-upload
For production systems, presigned S3/GCS URLs are strongly preferred. The client uploads directly to object storage — the GraphQL server never handles the binary stream, eliminating memory pressure and simplifying horizontal scaling.

🧠 Why are presigned upload URLs preferred over streaming uploads through a GraphQL resolver?

Presigned URLs are required by the GraphQL spec
Presigned URLs bypass the GraphQL server entirely — the client uploads directly to object storage, eliminating memory pressure, binary streaming complexity, and horizontal scaling concerns from the API layer
graphql-upload is deprecated and no longer maintained

Real-world Resolver Patterns

Production resolvers are layered — they validate context, delegate to a DataSource or service layer, handle partial errors, and never expose raw database errors to clients.

The Resolver Responsibility Stack

GraphQL Resolver (thin — orchestrate only) │ ▼ Service Layer (business logic, validation, auth checks) │ ▼ DataSource / Repository (DB / REST API / cache) │ ▼ Database / External Service

Pattern: Resolver Delegation

// ❌ Fat resolver — business logic mixed with data access
const resolvers = {
  Mutation: {
    async createOrder(_, { input }, ctx) {
      if (!ctx.user) throw new GraphQLError('Unauthorized');
      if (input.items.length === 0) throw new GraphQLError('Empty order');
      const total = input.items.reduce((s, i) => s + i.price * i.qty, 0);
      const order = await ctx.db.query('INSERT INTO orders ...');
      await ctx.emailSvc.sendConfirmation(order);
      return order;
    }
  }
};

// ✅ Thin resolver — delegates to service
const resolvers = {
  Mutation: {
    createOrder: (_, { input }, ctx) => ctx.services.order.create(ctx.user, input)
  }
};

Handling Partial Errors

// Return partial data + errors array in same response
const resolvers = {
  Query: {
    async dashboard(_, __, ctx) {
      const [user, orders, recommendations] = await Promise.allSettled([
        ctx.dataSources.userAPI.getUser(ctx.user.id),
        ctx.dataSources.orderAPI.getOrders(ctx.user.id),
        ctx.dataSources.recAPI.getRecommendations(ctx.user.id)
      ]);

      return {
        user:            user.status === 'fulfilled' ? user.value : null,
        orders:          orders.status === 'fulfilled' ? orders.value : [],
        recommendations: recommendations.status === 'fulfilled' ? recommendations.value : []
      };
    }
  }
};

🧠 Why should resolvers be "thin" and delegate to a service layer?

GraphQL requires resolvers to be less than 10 lines
Thin resolvers keep business logic testable and reusable independently of the GraphQL transport layer — the same service can be called from REST, jobs, or tests without invoking the GraphQL executor
Fat resolvers cause memory leaks

Schema Design at Scale Interview Q19

Schema design decisions made early are hard to undo. Naming conventions, nullability, input types vs inline arguments, and domain modeling all affect long-term maintainability.

Nullability Strategy

# ❌ Over-nullable — every field is optional, clients must null-check everything
type User {
  id:    ID
  name:  String
  email: String
}

# ✅ Explicit nullability — non-null for fields that are ALWAYS present
type User {
  id:    ID!      # always exists — non-null
  name:  String!  # always exists — non-null
  email: String   # optional — user may not have verified email
}

# ❌ Inline argument explosion
type Mutation {
  createUser(name: String!, email: String!, age: Int!, role: String!): User!
}

# ✅ Input types — groupable, reusable, versionable
input CreateUserInput { name: String!; email: String!; age: Int!; role: String! }
type Mutation {
  createUser(input: CreateUserInput!): User!
}

Domain Modeling Best Practices

PatternRecommendation
NamingUse domain language — Order, not OrderEntity; cancel, not setStatusCancelled
MutationsReturn the mutated object (not just a boolean) — enables cache updates
Union return typesUse unions for mutations: CreateUserResult = User | ValidationError | DuplicateError
Relay IDsUse globally unique IDs (base64(type:id)) for cross-service caching

🧠 Why should GraphQL mutations return the mutated object rather than a boolean?

To reduce query complexity scores
Returning the full updated object allows clients (Apollo Client, urql) to automatically update their local cache without a separate refetch — improving UI consistency and reducing network round-trips
Boolean return types are banned in the GraphQL spec

GraphQL Clients — Apollo & urql

Choosing and configuring the right GraphQL client — Apollo Client, urql, or a lightweight fetch wrapper — has a major impact on caching behaviour, bundle size, and developer experience.

Apollo Client Setup

import { ApolloClient, InMemoryCache, HttpLink, from } from '@apollo/client';
import { onError } from '@apollo/client/link/error';

const errorLink = onError(({ graphQLErrors, networkError }) => {
  if (graphQLErrors)
    graphQLErrors.forEach(({ message, extensions }) =>
      logger.error({ code: extensions?.code }, message));
  if (networkError) logger.error('Network error', networkError);
});

export const client = new ApolloClient({
  link: from([errorLink, new HttpLink({ uri: '/graphql', credentials: 'include' })]),
  cache: new InMemoryCache({
    typePolicies: {
      User: { keyFields: ['id'] }  // cache normalization by id
    }
  })
});

Normalized Cache
Apollo's InMemoryCache normalizes by __typename + id. When a mutation returns a User with the same id, every query referencing that user updates automatically — this is why mutations should return the full object.

🧠 What is cache normalization in Apollo Client and why does it matter?

It compresses cached data to save memory
It stores each entity once, keyed by __typename:id. When any query returns the same entity, all components subscribed to it re-render automatically — eliminating stale data across different queries that reference the same object
It encrypts queries before sending to the server

formatError — sanitize production errors

const server = new ApolloServer({
  schema,
  formatError(formattedError, error) {
    // Log original error server-side
    logger.error(error);

    // Strip stack traces and internal details from client response
    if (formattedError.extensions?.code === 'INTERNAL_SERVER_ERROR') {
      return { message: 'Internal server error', extensions: { code: 'INTERNAL_SERVER_ERROR' } };
    }
    return formattedError;
  }
});
