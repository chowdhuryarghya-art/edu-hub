Welcome

Welcome & Node.js Architecture

Node.js is a JavaScript runtime built on Chrome's V8 engine. Its non-blocking, event-driven model makes it ideal for I/O-intensive APIs and microservices.

What Makes Node.js Different

Traditional server (Java/PHP/Ruby): Thread per request → 1,000 connections = 1,000 threads = ~4GB RAM Node.js architecture: Single Thread + Non-blocking I/O + Event Loop = 1,000 connections on ONE thread with minimal memory Why? Node delegates I/O to the OS; it only runs JS when data is ready

Node.js Runtime Stack

Your JavaScript Code (application logic) │ Node.js APIs (fs, http, crypto, path…) │ V8 Engine (compiles JS → machine code, GC) │ libuv (event loop, thread pool, async I/O) │ OS (epoll/kqueue/IOCP — actual I/O)

When to Use Node.js

✅ Great For❌ Avoid For
REST/GraphQL APIs with high concurrencyCPU-intensive computation (video encoding, ML inference)
Real-time apps (WebSockets, SSE)Long-running CPU loops that block the event loop
I/O-bound microservicesHeavy matrix math (use Python/NumPy instead)
Streaming data pipelinesAnything requiring strict type safety at runtime (use TypeScript)

Q: Why can Node.js handle thousands of concurrent connections on a single thread?

A) It uses green threads internally to parallelize work
B) V8 is extremely fast at switching between requests
C) I/O operations are delegated to the OS — Node only runs JS when data is ready, so the thread is never blocking
D) Node.js uses multiple cores automatically via the cluster module
✓ Correct! Node's non-blocking I/O model lets the event loop register interest in I/O with the OS, then continue serving other requests while the OS waits for data.

JS Async: Callbacks → Promises → Async/Await

The evolution of async JavaScript is a core interview topic — know the problems each pattern solves and when to use each.

Callbacks — The Original Pattern

const fs = require('fs');



// Node-style callback: (err, data) pattern

fs.readFile('data.txt', 'utf8', (err, data) => {

  if (err) return console.error(err);

  console.log(data);

});



// Callback hell — nested callbacks become unreadable

db.getUser(id, (err, user) => {

  db.getOrders(user.id, (err, orders) => {

    db.getItems(orders[0].id, (err, items) => {

      // pyramid of doom...

    });

  });

});

Promises

const fs = require('fs/promises');



// Sequential

const data = await fs.readFile('data.txt', 'utf8');



// Parallel — both start concurrently

const [a, b] = await Promise.all([

  fs.readFile('a.txt', 'utf8'),

  fs.readFile('b.txt', 'utf8'),

]);



// allSettled — wait for all, don't fail-fast

const results = await Promise.allSettled([p1, p2, p3]);

results.forEach(r => {

  if (r.status === 'fulfilled') process(r.value);

  else logger.warn(r.reason);

});



// race — first to settle wins

const result = await Promise.race([fetchFromPrimary(), fetchFromFallback()]);

Async/Await Anti-patterns

// ❌ Sequential when parallel is possible

const user = await getUser(id);

const orders = await getOrders(id);  // waits unnecessarily



// ✅ Parallel — save ~50% time

const [user, orders] = await Promise.all([getUser(id), getOrders(id)]);



// ❌ await in forEach — doesn't wait for each iteration

items.forEach(async item => { await process(item); });  // WRONG



// ✅ Use for...of for sequential async iteration

for (const item of items) { await process(item); }



// ✅ Or Promise.all for parallel (if order doesn't matter)

await Promise.all(items.map(item => process(item)));

Q: What is the key difference between Promise.all() and Promise.allSettled()?

A) Promise.all is faster since it stops on first result
B) Promise.all rejects immediately if any promise rejects; allSettled always waits for all, returning each outcome (fulfilled or rejected)
C) They are identical — different names for the same behavior
D) allSettled only works with arrays of the same type
✓ Correct! Use allSettled when you need ALL results regardless of failures — perfect for batch operations where partial success is acceptable.

Modules: CommonJS vs ESM

Node.js has two module systems. Knowing their differences, gotchas, and interop rules is a common senior interview topic.

CommonJS vs ES Modules

CommonJS (CJS)ES Modules (ESM)
Syntaxrequire() / module.exportsimport / export
LoadingSynchronousAsynchronous
BindingDynamic (runtime)Static (parse time)
Tree shaking❌✅
Top-level await❌✅
__dirname✅❌ use import.meta.url
Can import CJS?—✅ (as default export)
Can require ESM?❌—
// === CommonJS ===

// math.js

function add(a, b) { return a + b; }

module.exports = { add };



// app.js

const { add } = require('./math');

// require() is synchronous AND cached — same object returned every time

require('./math') === require('./math')  // true



// === ES Modules ===

// math.mjs  (or set "type":"module" in package.json)

export function add(a, b) { return a + b; }

export default 42;



// app.mjs

import { add } from './math.mjs';



// __dirname equivalent in ESM

import { fileURLToPath } from 'url';

import { dirname } from 'path';

const __filename = fileURLToPath(import.meta.url);

const __dirname = dirname(__filename);



// Top-level await (ESM only)

const config = await loadConfig();  // works at module top level
Interop Gotcha
You cannot require() an ES Module from CJS — you'll get ERR_REQUIRE_ESM. CJS can be imported in ESM as a default export. When writing new packages, prefer ESM with a CJS wrapper via "exports" field in package.json for dual mode.

Q: Can you use top-level await in a CommonJS module?

A) Yes — it works in Node.js 18+
B) No — top-level await is exclusive to ES Modules
C) Only with the --experimental-top-level-await flag
D) Yes, using an IIFE async wrapper pattern
✓ Correct! Top-level await is an ESM-only feature. In CJS you must wrap in an async IIFE: (async () => { const x = await ...; })();

HTTP & Express Fundamentals

Express is the most-used Node.js web framework — mastering its routing, middleware chain, and error handling is essential for any backend role.

Production Express Setup

const express = require('express');

const helmet = require('helmet');

const pino = require('pino-http');



const app = express();



// Security headers

app.use(helmet());

// Request logging

app.use(pino());

// JSON body parser with size limit

app.use(express.json({ limit: '100kb' }));

// Disable x-powered-by header

app.disable('x-powered-by');



// Route handler with async error handling

app.get('/users/:id', asyncHandler(async (req, res) => {

  const user = await userService.findById(req.params.id);

  if (!user) return res.status(404).json({ error: 'User not found' });

  res.json(user);

}));



// 4-param error handler — MUST be last middleware

app.use((err, req, res, next) => {

  req.log.error({ err }, 'Unhandled error');

  res.status(err.status || 500).json({ error: 'Internal Server Error' });

});



// asyncHandler wrapper — catches async errors and calls next(err)

const asyncHandler = fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

Express Middleware Chain

Request → helmet() → pino() → json() → router → handler ↓ (if error thrown) Error Handler (4 params)
Interview Tip
Express detects error-handling middleware by counting parameters — the function must have exactly 4 params (err, req, res, next). Missing one means Express treats it as a regular middleware and errors pass right through.

Q: Why must Express error-handling middleware have exactly 4 parameters?

A) It's just a naming convention with no functional impact
B) Express identifies error handlers by parameter count — 4 params (err, req, res, next) signals error-handling mode
C) The 4th param next is needed to pass errors to subsequent handlers
D) Three-param middleware can't access the error object
✓ Correct! Express uses Function.length (parameter count) to distinguish error handlers. A 3-param signature makes Express skip it as a regular middleware even if named err.

Event Loop Deep Dive

The event loop is the heart of Node.js. Understanding its six phases lets you reason about execution order, avoid starvation, and write code that never blocks the thread.

The Six Phases

┌──────────────────────────────────┐ │ Event Loop │ └───────────────┬──────────────────┘ │ ┌───────────▼────────────┐ │ 1. timers │ setTimeout / setInterval callbacks └───────────┬────────────┘ ┌───────────▼────────────┐ │ 2. pending I/O │ deferred I/O callbacks └───────────┬────────────┘ ┌───────────▼────────────┐ │ 3. idle / prepare │ internal use only └───────────┬────────────┘ ┌───────────▼────────────┐ │ 4. poll │ fetch new I/O events (blocks here if empty) └───────────┬────────────┘ ┌───────────▼────────────┐ │ 5. check │ setImmediate callbacks └───────────┬────────────┘ ┌───────────▼────────────┐ │ 6. close callbacks │ socket.on('close') etc. └────────────────────────┘ Between each phase: nextTick queue drains, then Promise microtask queue

Execution Order Example

console.log('1 — sync');



setTimeout(() => console.log('5 — timer'), 0);



Promise.resolve().then(() => console.log('3 — microtask'));



process.nextTick(() => console.log('2 — nextTick'));



setImmediate(() => console.log('4 — setImmediate (check phase)'));



// Output: 1  2  3  4  5
Key Priority Order
Sync → nextTick → Microtasks (Promises) → Timers → setImmediate → I/O → Close. process.nextTick fires before Promise microtasks — a classic interview gotcha.

Q: You call Promise.resolve().then(A) and process.nextTick(B). Which runs first?

A) A — Promise microtasks have higher priority
B) They run concurrently
C) B — process.nextTick queue drains before the Promise microtask queue
D) Timer phase runs first
✓ Correct! process.nextTick has higher priority than Promise microtasks — a detail that trips up many candidates.

libuv & Thread Pool

libuv is the C library that powers Node.js async I/O. Understanding its thread pool helps you diagnose latency spikes and tune concurrency for file, crypto, and DNS operations.

libuv Thread Pool Architecture

JS Main Thread (event loop) │ │ delegates work that can't use kernel async ▼ libuv Thread Pool (default: 4 threads, max: 1024) ┌──────────┬──────────┬──────────┬──────────┐ │Thread 1 │Thread 2 │Thread 3 │Thread 4 │ └────┬─────┴────┬─────┴────┬─────┴────┬─────┘ │ │ │ │ fs.read crypto dns.lookup zlib Kernel-native async (no thread pool): TCP/UDP sockets, HTTP, timers, signals

Tuning the Thread Pool

# Must be set BEFORE Node.js starts

UV_THREADPOOL_SIZE=16 node server.js



# Or as the very first line of code

process.env.UV_THREADPOOL_SIZE = '16';  // must be synchronous, at top of entry file
Pool Saturation
If all 4 threads are busy (e.g., 4 concurrent bcrypt.hash() calls), the 5th queues and adds latency to every subsequent request. Increase UV_THREADPOOL_SIZE to match your concurrency profile, or move CPU work to worker_threads.

Q: What is the default libuv thread pool size?

A) 1 thread
B) 4 threads
C) Matches the number of CPU cores
D) 128 threads
✓ Correct! Default is 4 threads, configurable via UV_THREADPOOL_SIZE up to 1024.

Streams & Buffers

Streams let you process data piece-by-piece without loading everything into memory — essential for file downloads, log pipelines, and proxying at scale.

Stream Types

TypeExampleKey Events/Methods
Readablefs.createReadStreamdata, end, pipe()
Writableres, fs.createWriteStreamwrite(), end(), drain
DuplexTCP socketBoth readable & writable
Transformzlib.createGzip()Modifies data in-flight

Stream Pipeline (production pattern)

const { pipeline } = require('stream/promises');

const fs = require('fs');

const zlib = require('zlib');



// Stream + gzip compress without loading into memory

app.get('/download', async (req, res) => {

  res.setHeader('Content-Encoding', 'gzip');

  await pipeline(

    fs.createReadStream('./data.csv'),

    zlib.createGzip(),

    res

  );

  // pipeline() handles back-pressure AND propagates errors

});
pipe() vs pipeline()
pipe() does NOT propagate errors between streams — a read error won't close the write stream, leaking resources. Always use stream.pipeline() (or its promise wrapper) in production.

Q: Why is stream.pipeline() preferred over .pipe() in production?

A) pipeline() is faster due to native C++ bindings
B) pipe() requires more memory
C) pipeline() properly propagates errors and destroys all streams on failure; pipe() silently leaks streams on error
D) No functional difference
✓ Correct! stream.pipeline() is the production-safe choice — error propagation and cleanup are handled automatically.

Error Handling Patterns

Unhandled errors crash processes in production. Senior engineers design an airtight error taxonomy and propagation strategy before writing the first route.

Error Taxonomy

TypeExampleCorrect Response
OperationalDB timeout, invalid inputLog & return error response — recoverable
ProgrammerTypeError: null.xCrash & restart — indicates a bug
Unhandled rejectionMissing await + .catch()Global handler → log → exit(1)

Production Error Setup

class AppError extends Error {

  constructor(message, statusCode = 500) {

    super(message);

    this.statusCode = statusCode;

    this.isOperational = true;

  }

}



// Wrap async route handlers

const wrap = fn => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);



router.get('/user/:id', wrap(async (req, res) => {

  const user = await db.findById(req.params.id);

  if (!user) throw new AppError('Not found', 404);

  res.json(user);

}));



// Global safety net

process.on('unhandledRejection', (err) => { logger.fatal(err); process.exit(1); });

process.on('uncaughtException',  (err) => { logger.fatal(err); process.exit(1); });
Never Swallow Errors
An empty catch(() => {}) silently masks bugs. Always: log the error, decide if it's recoverable, and either respond with a safe message or crash fast.

Q: An operational error vs a programmer error — how should each be handled?

A) Both should crash the process
B) Both should be caught and logged silently
C) Operational errors are recoverable — log and respond. Programmer errors indicate a bug — crash and let the process manager restart
D) No distinction is needed in modern Node.js
✓ Correct! This distinction is the foundation of production-grade Node.js error handling. Continuing after a programmer error risks data corruption.

Worker Threads & Clustering

Two complementary tools for scaling CPU utilization: worker_threads for in-process parallelism, and cluster / PM2 to leverage all CPU cores for HTTP throughput.

Worker Threads

// main.js — offload CPU work without blocking the event loop

const { Worker } = require('worker_threads');



function runWorker(workerFile, data) {

  return new Promise((resolve, reject) => {

    const w = new Worker(workerFile, { workerData: data });

    w.on('message', resolve);

    w.on('error',   reject);

    w.on('exit', code => { if(code !== 0) reject(new Error(`exit ${code}`)); });

  });

}



// worker.js

const { workerData, parentPort } = require('worker_threads');

parentPort.postMessage(heavyCompute(workerData));

Cluster Mode with PM2

# ecosystem.config.js

module.exports = {

  apps: [{

    name: 'api',

    script: './dist/server.js',

    instances: 'max',   // one per CPU core

    exec_mode: 'cluster',

    max_memory_restart: '512M'

  }]

};



# Start / reload without downtime

pm2 start ecosystem.config.js

pm2 reload api  # zero-downtime reload
Workers vs Cluster
Worker Threads share the same process memory and are ideal for CPU-intensive work inside a single request (e.g., image processing). Cluster creates independent OS processes with separate memory — it distributes TCP connections and achieves true horizontal scaling on multi-core machines.

Q: When should you choose worker_threads over cluster?

A) When you need multiple HTTP ports
B) They are equivalent — pick either
C) Use workers to offload a CPU-intensive task within a single request without blocking the event loop; use cluster to replicate the whole server across CPU cores
D) cluster is deprecated
✓ Correct! The two solve orthogonal problems. In practice, many production apps use both: cluster for horizontal scaling and worker threads for occasional heavy computation.

Memory Leaks & Diagnostics

Memory leaks in long-running Node.js servers cause steadily growing RSS, slower GC, and eventual OOM crashes. Knowing how to detect and fix them is a senior-level skill.

Common Leak Sources

SourceExampleFix
Global accumulationPushing to a module-level array foreverBound the collection; use a cache with TTL
Event listener leakemitter.on() in a loop without off()Always call removeListener or use once()
Closure capturing large objectsLong-lived callback holds a reference to a requestNullify after use; restructure scope
Uncleaned timerssetInterval never clearedAlways store the handle and call clearInterval

Interview Approach
When asked to debug a memory leak: (1) monitor RSS over time with metrics, (2) take two heap snapshots, (3) compare allocations between snapshots, (4) look for growing retained objects. Common culprits: maps, arrays, event emitters.

Q: What is the most common cause of event listener memory leaks in Node.js?

A) Using async/await inside event handlers
B) Attaching listeners with once()
C) Calling emitter.on() repeatedly (e.g., on each request) without a corresponding removeListener(), causing listener count to grow unboundedly
D) Emitters with more than 10 listeners always leak
✓ Correct! Node.js warns when an emitter exceeds 10 listeners (MaxListenersExceededWarning) — this is often a sign of a leak. Use emitter.setMaxListeners() only after confirming the high count is intentional.

Graceful Shutdown

A graceful shutdown drains in-flight requests, closes DB connections, and flushes log buffers before the process exits — preventing data corruption and dropped responses during deploys.

The Shutdown Sequence

SIGTERM received (from k8s / PM2 / systemd) │ ▼ 1. Stop accepting new requests server.close() │ ▼ 2. Drain in-flight requests wait for existing handlers to finish │ ▼ 3. Close downstream connections DB pool, Redis, message queue │ ▼ 4. Flush logs & metrics │ ▼ process.exit(0)

Implementation

const server = app.listen(3000, '127.0.0.1');



async function shutdown(signal) {

  logger.info({ signal }, 'Shutdown initiated');



  // 1. Stop accepting new TCP connections

  await new Promise(r => server.close(r));



  // 2. Close DB & cache connections

  await db.end();

  await redis.quit();



  logger.info('Shutdown complete');

  process.exit(0);

}



process.on('SIGTERM', () => shutdown('SIGTERM'));

process.on('SIGINT',  () => shutdown('SIGINT'));



// Kubernetes: set terminationGracePeriodSeconds to allow drain time
Kubernetes & Readiness Probes
When a pod receives SIGTERM, the load balancer may still route traffic for a few seconds. Add a short sleep (1-2s) before server.close(), or use a readiness probe that immediately returns 503 on shutdown to prevent new connections from arriving.

Q: Why should you call server.close() first during a graceful shutdown?

A) It immediately kills all open sockets
B) It flushes the log buffer
C) It stops the server from accepting new connections while allowing existing requests to complete — preventing new work from starting while the process winds down
D) It sends SIGTERM to worker processes
✓ Correct! server.close(cb) stops new connections and calls cb once all existing connections are closed — the callback is your signal to proceed with teardown.

Middleware Patterns

const requireRole = (...roles) => (req, res, next) => {

D) Use app.use({ methods: ['POST'] }, mw)
✓ Correct! Either check req.method inside the middleware and skip via next(), or register the middleware only on specific method handlers (e.g., router.post('/path', mw, handler)).

Testing: Jest & Supertest

A strong test pyramid — unit, integration, and contract tests — is the mark of a production-ready Node.js codebase. Supertest lets you test Express routes without starting a real server.

Test Pyramid

E2E / Contract (few — slow, expensive) /\ / \ Integration (moderate — test routes & DB) / \ / \ Unit Tests (many — fast, isolated)

Integration Test with Supertest

// user.routes.test.ts

import request from 'supertest';

import { app } from '../src/app';



describe('GET /api/users/:id', () => {

  it('returns 200 for existing user', async () => {

    const res = await request(app).get('/api/users/1')

      .set('Authorization', `Bearer ${testToken}`);

    expect(res.status).toBe(200);

    expect(res.body).toMatchObject({ id: '1', name: expect.any(String) });

  });



  it('returns 404 for missing user', async () => {

    const res = await request(app).get('/api/users/9999');

    expect(res.status).toBe(404);

  });

});
Export app separately from listen()
Export the Express app object from a file that does NOT call app.listen(). A separate server.ts calls listen. This lets Supertest bind the app on an ephemeral port without side effects during tests.

Q: Why should the Express app be exported from a file that doesn't call app.listen()?

A) listen() causes memory leaks in Jest
B) Supertest cannot use an app that has already bound a port
C) Separating app creation from server startup lets Supertest bind the app on a random port without conflicting with a real server, and makes the file importable without side effects
D) Jest mocks app.listen() automatically
✓ Correct! This is a fundamental Node.js testability pattern. app.ts configures the Express instance; server.ts calls app.listen(). Tests import only app.ts.

Caching with Redis

Redis is the standard caching layer for Node.js APIs. Mastering cache-aside, cache invalidation, and TTL strategies is essential for high-traffic services.

Cache-Aside Pattern

import { createClient } from 'redis';

const redis = createClient({ url: process.env.REDIS_URL });

await redis.connect();



async function getUser(id: string) {

  const cacheKey = `user:${id}`;



  // 1. Check cache

  const cached = await redis.get(cacheKey);

  if (cached) return JSON.parse(cached);



  // 2. Miss — fetch from DB

  const user = await db.findById(id);

  if (!user) return null;



  // 3. Populate cache with TTL (5 minutes)

  await redis.setEx(cacheKey, 300, JSON.stringify(user));

  return user;

}



// Invalidate on update

async function updateUser(id: string, data: Partial<User>) {

  const user = await db.update(id, data);

  await redis.del(`user:${id}`);  // invalidate cache

  return user;

}
Cache Stampede
When a popular key expires, many requests hit the DB simultaneously. Mitigate with: (1) SETNX mutex locking — only one request rebuilds the cache; (2) probabilistic early expiration; (3) background refresh before TTL expires.

Q: What is a cache stampede and how do you prevent it?

A) When Redis runs out of memory
B) When a Redis cluster fails over
C) When a popular cached key expires and many concurrent requests all miss the cache and hit the DB simultaneously — prevented by mutex locking (SETNX), background refresh, or probabilistic expiration
D) When the cache is too large
✓ Correct! The mutex approach: set a lock key before DB fetch, other requesters wait or serve stale data. Use SET key value NX EX 10 as an atomic lock in Redis.

Database Patterns & N+1

The N+1 query problem silently kills performance. Understanding eager loading, DataLoader batching, and connection pooling separates senior from junior backend developers.

The N+1 Problem

// ❌ N+1: 1 query for users + N queries for each user's posts

const users = await db.query('SELECT * FROM users');  // 1 query

for (const user of users) {

  user.posts = await db.query('SELECT * FROM posts WHERE user_id = $1', [user.id]); // N queries!

}



// ✅ Fix 1: JOIN (single query)

const result = await db.query(`

  SELECT u.*, json_agg(p.*) AS posts

  FROM users u

  LEFT JOIN posts p ON p.user_id = u.id

  GROUP BY u.id

`);



// ✅ Fix 2: Batch query (DataLoader pattern)

const userIds = users.map(u => u.id);

const posts = await db.query('SELECT * FROM posts WHERE user_id = ANY($1)', [userIds]);

// Then group posts by user_id in memory — 2 queries total

Connection Pooling with pg

import { Pool } from 'pg';

const pool = new Pool({

  connectionString: process.env.DATABASE_URL,

  max: 20,          // max connections in pool

  idleTimeoutMillis: 30000,

  connectionTimeoutMillis: 2000

});

// Always release connections — use pool.query() or client from pool.connect()

Q: What causes the N+1 problem and what is the most efficient solution?

A) Using async/await in database calls
B) Using an ORM instead of raw SQL
C) Fetching a list, then making one query per item for related data. Fix: use a JOIN or a single batch query to fetch all related data at once, then join in memory
D) Having more than 100 rows in a result set
✓ Correct! N+1 turns O(1) DB work into O(N). Use JOINs, batch queries, or DataLoader to reduce N queries to 1 or 2.

Cursor-based Pagination

// GET /api/v1/users?cursor=xxx&limit=20

router.get('/users', wrap(async (req, res) => {

  const limit = Math.min(Number(req.query.limit) || 20, 100);

  const cursor = req.query.cursor as string;



  const users = await db.query(`

    SELECT * FROM users

    WHERE id > $1

    ORDER BY id ASC LIMIT $2

  `, [cursor || 0, limit + 1]);  // fetch one extra to detect hasNext



  const hasNext = users.length > limit;

  if (hasNext) users.pop();



  res.json({

    data: users,

    pagination: {

      hasNext,

      nextCursor: hasNext ? users[users.length - 1].id : null

    }

  });

}));

Q: Why is cursor-based pagination preferred over offset-based for large datasets?

A) Cursor pagination is easier to implement
B) Offset pagination requires a Redis cache
C) Offset pagination performs a full table scan up to the offset (O(n)); cursor pagination uses a WHERE clause on an indexed column making each page O(log n). Cursors also avoid duplicates when rows are inserted between pages.
D) Cursor pagination supports random access to any page
✓ Correct! OFFSET 10000 tells the DB to scan and discard 10,000 rows — it's O(n). A WHERE clause on an indexed column is O(log n). Cursor pagination also handles live data insertion correctly.
