Spring Boot is the de-facto standard for building production-grade Java microservices. It eliminates boilerplate through convention-over-configuration, auto-wiring, and an opinionated starter ecosystem.

IoC & Dependency Injection

Inversion of Control is the backbone of Spring. Instead of objects creating their dependencies, the container injects them — enabling testability, loose coupling, and declarative configuration.

DI Styles — Constructor vs Field vs Setter

// ✅ PREFERRED: Constructor injection — immutable, testable without Spring
@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentService paymentService;

    public OrderService(OrderRepository orderRepository, PaymentService paymentService) {
        this.orderRepository = orderRepository;
        this.paymentService = paymentService;
    }
}

// ❌ Field injection — hides dependencies, can't test without Spring context
@Service
public class BadService {
    @Autowired
    private OrderRepository orderRepository;  // avoid this
}

// Setter injection — useful for optional/reconfigurable dependencies only
@Service
public class NotificationService {
    private EmailClient emailClient;

    @Autowired
    public void setEmailClient(EmailClient emailClient) {
        this.emailClient = emailClient;
    }
}

Qualifier & Primary

// Multiple beans of the same type
@Bean
@Primary
public NotificationSender emailSender() { return new EmailSender(); }

@Bean
public NotificationSender smsSender() { return new SmsSender(); }

// Inject a specific one by name
public AlertService(@Qualifier("smsSender") NotificationSender sender) {
    this.sender = sender;
}

// Spring 6.1+: @Autowired with @Qualifier on constructor param
public ReportService(
        @Qualifier("pdfRenderer") ReportRenderer renderer) { ... }
Interview Gotcha
When there are multiple beans of the same type and no @Primary or @Qualifier, Spring throws NoUniqueBeanDefinitionException. Interviewers will ask how to resolve it — know all three approaches: @Primary, @Qualifier, and matching parameter name to bean name.

Q: Why is constructor injection preferred over field injection?

A) It is faster at runtime
B) It requires less code
C) It makes dependencies explicit and final, allows the class to be instantiated without a Spring context in unit tests, and prevents circular dependency at startup
D) Spring requires it in Boot 3.x
✓ Correct! Constructor injection enforces immutability (final fields), makes all required dependencies visible in the API, and lets you write plain JUnit tests with new OrderService(mockRepo, mockPayment) — no Spring context needed.

Spring Beans & Application Context

Understanding bean lifecycle, scopes, and the ApplicationContext is essential for diagnosing startup failures and memory issues in production.

Bean Lifecycle

Instantiation → Populate Properties → setBeanName() → setBeanFactory() → setApplicationContext() → @PostConstruct / afterPropertiesSet() → Bean Ready (in Use) → @PreDestroy / destroy() → Destroyed
@Component
public class CacheWarmer {
    private final CacheService cacheService;

    public CacheWarmer(CacheService cacheService) {
        this.cacheService = cacheService;
    }

    @PostConstruct  // runs after all dependencies injected
    public void warmUp() {
        cacheService.preload();
    }

    @PreDestroy  // runs before bean is removed from context
    public void evict() {
        cacheService.evictAll();
    }
}

// Programmatic context access (avoid in application code)
@Component
public class BeanLookup implements ApplicationContextAware {
    private ApplicationContext ctx;

    @Override
    public void setApplicationContext(ApplicationContext ctx) {
        this.ctx = ctx;
    }
}
Circular Dependency
Spring Boot 2.6+ fails fast on circular dependencies by default. Fix by refactoring (split the bean, extract an interface), using @Lazy on one injection point, or restructuring to event-driven communication. Never use spring.main.allow-circular-references=true as a permanent fix.

Q: What is the default bean scope in Spring and what are its implications?

A) Prototype — a new instance is created on every injection
B) Singleton — one instance per ApplicationContext, shared across all injection points; beans must be stateless
C) Request — tied to the current HTTP request lifecycle
D) Thread — one instance per executing thread
✓ Correct! Singleton scope means all callers share the same bean instance — which is fine for stateless services but dangerous if you store mutable request-specific state in instance fields.

Auto-Configuration & Starters

Auto-configuration is Spring Boot's superpower — it reads the classpath, environment, and existing beans to wire up sensible defaults. Understanding how it works lets you override it precisely.

How Auto-Configuration Works

@SpringBootApplication │ ▼ @EnableAutoConfiguration │ ▼ Loads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports │ ▼ Each AutoConfiguration class has @ConditionalOn* guards: @ConditionalOnClass — class is on classpath? @ConditionalOnMissingBean — no user-defined bean yet? @ConditionalOnProperty — property set to value? │ ▼ Beans created only when conditions pass

Custom Auto-Configuration

// Your library's auto-configuration
@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean  // user can override with their own bean
    public AuditService auditService(AuditProperties props) {
        return new DefaultAuditService(props.getEndpoint());
    }
}

// Bind properties to a typed POJO

}

Security
Never put secrets (DB passwords, API keys, JWT secrets) in application.yml or check them into version control. Use environment variables, Kubernetes Secrets, or a secrets manager (HashiCorp Vault, AWS Secrets Manager). Spring Cloud Vault or AWS Parameter Store integrations handle this automatically.

Q: What is the correct way to override server.port for a containerised production deployment?

A) Edit application.properties before building the JAR
B) Use a @PropertySource annotation pointing to an external file
C) Set the SERVER_PORT environment variable or pass --server.port=8080 as a JVM argument — both override the in-JAR defaults without rebuilding
D) Use Spring Cloud Config and restart the app
✓ Correct! OS environment variables and command-line arguments sit at the top of Spring Boot's property source priority chain, so they always win without touching the packaged JAR — the 12-Factor way.

REST with Spring MVC

Spring MVC maps HTTP requests to handler methods via annotations. A production REST API must handle content negotiation, proper HTTP semantics, and DTOs to avoid leaking domain models.

Production REST Controller

@RestController
@RequestMapping("/api/v1/users")
@RequiredArgsConstructor  // Lombok — generates constructor injection
public class UserController {
    private final UserService userService;

    @GetMapping("/{id}")
    public ResponseEntity<UserResponse> getUser(@PathVariable Long id) {
        return userService.findById(id)
            .map(ResponseEntity::ok)
            .orElse(ResponseEntity.notFound().build());
    }

    @PostMapping
    public ResponseEntity<UserResponse> createUser(
            @RequestBody @Valid CreateUserRequest request,
            UriComponentsBuilder uriBuilder) {
        UserResponse created = userService.create(request);
        URI location = uriBuilder.path("/api/v1/users/{id}")
            .buildAndExpand(created.getId()).toUri();
        return ResponseEntity.created(location).body(created);
    }

    @PatchMapping("/{id}")
    public UserResponse updateUser(@PathVariable Long id,
            @RequestBody @Valid UpdateUserRequest request) {
        return userService.update(id, request);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void deleteUser(@PathVariable Long id) {
        userService.delete(id);
    }

    // Cursor-based pagination
    @GetMapping
    public Page<UserResponse> listUsers(
            @RequestParam(defaultValue = "0") int page,
            @RequestParam(defaultValue = "20") int size) {
        return userService.findAll(PageRequest.of(page, Math.min(size, 100)));
    }
}

DTO Pattern
Always map between domain entities and DTOs at the controller/service boundary. Returning JPA entities directly leaks the data model, triggers lazy-loading issues, and makes API versioning impossible. Use records (Java 16+) for immutable DTOs.

Q: What HTTP status code should a successful POST (resource creation) return?

A) 200 OK
B) 204 No Content
C) 201 Created, with a Location header pointing to the new resource's URI
D) 202 Accepted
✓ Correct! RFC 9110 mandates 201 Created for successful resource creation, with the Location header containing the URI of the newly created resource — enables clients to GET it immediately without a second lookup.

Validation & Exception Handling

A consistent error contract across all endpoints is the mark of a production API. Spring's validation framework combined with a global exception handler eliminates scattered try-catch blocks.

Bean Validation

// DTO with validation constraints
public record CreateUserRequest(
    @NotBlank(message = "Name is required")
    @Size(min = 2, max = 100)
    String name,

    @Email
    @NotBlank
    String email,

    @Min(18) @Max(120)
    Integer age,

    @Pattern(regexp = "^\\+?[1-9]\\d{7,14}$", message = "Invalid phone")
    String phone
) {}

// Custom constraint validator
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = UniqueEmailValidator.class)
public @interface UniqueEmail {
    String message() default "Email already registered";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

Global Exception Handler

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ErrorResponse handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors().stream()
            .collect(Collectors.toMap(
                FieldError::getField,
                fe -> Objects.requireNonNullElse(fe.getDefaultMessage(), "Invalid")
            ));
        return new ErrorResponse("VALIDATION_ERROR", "Validation failed", errors);
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponse handleNotFound(ResourceNotFoundException ex) {
        return new ErrorResponse("NOT_FOUND", ex.getMessage(), null);
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ErrorResponse handleGeneric(Exception ex) {
        log.error("Unhandled exception", ex);
        return new ErrorResponse("INTERNAL_ERROR", "An unexpected error occurred", null);
    }
}

// Consistent error body
public record ErrorResponse(String code, String message, Map<String, String> details) {}
Never Expose Internals
The generic handler must return a sanitised message — never propagate ex.getMessage() or stack traces to the client. Log the full exception server-side and return a fixed string to the caller.

Q: What is the difference between @ControllerAdvice and @RestControllerAdvice?

A) @RestControllerAdvice only handles exceptions from REST controllers
B) @ControllerAdvice is deprecated in Spring Boot 3
C) @RestControllerAdvice = @ControllerAdvice + @ResponseBody — handler return values are serialised to the response body automatically (JSON/XML), whereas @ControllerAdvice would need explicit @ResponseBody on each method
D) They are identical aliases
✓ Correct! @RestControllerAdvice is a composed annotation that adds @ResponseBody, making all exception handler methods automatically serialise their return value to JSON — the right choice for REST APIs.

Spring Data JPA & Hibernate

Spring Data JPA eliminates boilerplate DAO code while Hibernate manages the ORM mapping. Senior candidates must know the N+1 problem, fetch strategies, and when to drop down to native SQL.

Entity & Repository

@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE,
                    generator = "user_seq")
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    // FetchType.LAZY is the default for collections — use it!
    @OneToMany(mappedBy = "user", fetch = FetchType.LAZY, cascade = CascadeType.ALL)
    private List<Order> orders = new ArrayList<>();
}

// Repository with derived queries and custom JPQL
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);  // derived query

    // ✅ Fix N+1: JOIN FETCH loads orders in one query
    @Query("SELECT u FROM User u JOIN FETCH u.orders WHERE u.id = :id")
    Optional<User> findByIdWithOrders(@Param("id") Long id);

    // Projections — only fetch needed columns
    @Query("SELECT u.id as id, u.email as email FROM User u WHERE u.active = true")
    List<UserSummary> findAllActive();

    // Native SQL when JPQL isn't enough
    @Query(value = "SELECT * FROM users WHERE last_login < NOW() - INTERVAL '30 days'",
           nativeQuery = true)
    List<User> findInactiveUsers();
}

The N+1 Problem

// ❌ N+1: 1 query for users, then 1 per user for orders
List<User> users = userRepository.findAll();  // SELECT * FROM users
for (User u : users) {
    u.getOrders().size();  // SELECT * FROM orders WHERE user_id = ? (N times!)
}

// ✅ Fix 1: JOIN FETCH in JPQL
@Query("SELECT DISTINCT u FROM User u JOIN FETCH u.orders")
List<User> findAllWithOrders();

// ✅ Fix 2: @EntityGraph — declarative eager loading
@EntityGraph(attributePaths = {"orders", "orders.items"})
@Query("SELECT u FROM User u")
List<User> findAllWithOrdersAndItems();

// ✅ Fix 3: Batch fetching (hibernate.default_batch_fetch_size)
// spring.jpa.properties.hibernate.default_batch_fetch_size=16
Fetch Strategy Rules
Always use FetchType.LAZY on @OneToMany and @ManyToMany. Use JOIN FETCH or @EntityGraph at query time when you need the association. FetchType.EAGER on collections is a performance anti-pattern that cannot be un-eagered for queries that don't need the data.

Q: What causes the N+1 query problem in Hibernate and what is the most efficient fix?

A) Using @GeneratedValue strategy SEQUENCE
B) Using Optional return types in repositories
C) Accessing a LAZY collection in a loop triggers one SQL query per entity. Fix with JOIN FETCH or @EntityGraph to load associations in a single query, or set hibernate.default_batch_fetch_size to batch the child queries
D) Using the wrong cascade type
✓ Correct! N+1 is one of the most common performance killers in JPA applications — and the most common interview question. Always verify with Hibernate's SQL logging (spring.jpa.show-sql=true or better, datasource-proxy) to count queries.

Transactions & DB Migrations

Transactions guarantee data consistency. @Transactional is deceptively simple — its propagation, isolation, and proxy mechanics have many gotchas that senior engineers must know.

@Transactional Deep Dive

@Service
public class OrderService {

    // Default: PROPAGATION_REQUIRED, ISOLATION_DEFAULT, rollbackOn=RuntimeException
    @Transactional
    public Order placeOrder(OrderRequest req) {
        Order order = orderRepository.save(new Order(req));
        inventoryService.reserve(req.getItems());  // same TX by default
        paymentService.charge(req.getPayment());    // same TX
        return order;  // commits here if no exception
    }

    // Requires a NEW transaction — audit log always written, even on rollback
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void auditAction(String action) {
        auditRepository.save(new AuditLog(action));
    }

    // Read-only: Hibernate skips dirty-checking, DB can use read replica
    @Transactional(readOnly = true)
    public List<Order> getOrdersByUser(Long userId) {
        return orderRepository.findByUserId(userId);
    }
}

@Transactional Gotchas

GotchaExplanation
Self-invocationCalling this.method() skips the proxy — no transaction. Use a separate bean or AopContext.currentProxy()
Checked exceptionsOnly RuntimeException rolls back by default. Use rollbackFor = Exception.class for checked exceptions
Private methods@Transactional on private methods is silently ignored — proxy can't intercept them
LazyInitializationExceptionAccessing a lazy collection outside a transaction. Fix: open transaction, use DTO projection, or @Transactional on the service method

Q: You call a @Transactional method from another method in the same class. Will the transaction be applied?

A) Yes — Spring always applies the transaction regardless of call origin
B) No — self-invocation bypasses the Spring AOP proxy, so @Transactional is silently ignored. The fix is to inject the service into itself or use AopContext.currentProxy()
C) Only if both methods have @Transactional
D) Only in Spring Boot 3+
✓ Correct! Spring's transaction management works via a dynamic proxy wrapping the bean. When you call this.method(), you bypass the proxy entirely — this is the most common @Transactional gotcha in senior interviews.

Spring Security & JWT

Spring Security is a powerful, deeply configurable framework. A senior engineer must configure the SecurityFilterChain correctly, implement stateless JWT auth, and understand the CSRF trade-offs.

Security Filter Chain (Spring Boot 3 / Security 6)

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http,
            JwtAuthFilter jwtFilter) throws Exception {
        return http
            .csrf(AbstractHttpConfigurer::disable)  // stateless JWT — no CSRF needed
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/auth/**", "/actuator/health").permitAll()
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);  // cost factor 12 for production
    }
}

JWT Filter

@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {
    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain) throws IOException, ServletException {
        String authHeader = req.getHeader("Authorization");
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            chain.doFilter(req, res);
            return;
        }
        String jwt = authHeader.substring(7);
        String username = jwtService.extractUsername(jwt);
        if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
            UserDetails user = userDetailsService.loadUserByUsername(username);
            if (jwtService.isTokenValid(jwt, user)) {
                UsernamePasswordAuthenticationToken authToken =
                    new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                authToken.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                SecurityContextHolder.getContext().setAuthentication(authToken);
            }
        }
        chain.doFilter(req, res);
    }
}
JWT Best Practices
Use short-lived access tokens (15 min) and refresh tokens (7 days) stored in HttpOnly cookies. Sign with RS256 (asymmetric) for microservices so each service can verify without a shared secret. Always validate exp, iss, and aud claims.

Q: Why can CSRF protection be disabled for a stateless JWT REST API?

A) JWT tokens are inherently CSRF-proof
B) Spring Security 6 disables CSRF by default
C) CSRF attacks exploit session cookies — a browser automatically attaches them. When auth is done via Authorization: Bearer header (not cookies), a malicious site cannot set that header, so CSRF is not a vector
D) REST APIs are not affected by CSRF attacks
✓ Correct! CSRF only applies when credentials are in cookies (the browser auto-sends them cross-origin). JWTs in Authorization headers are not auto-sent by the browser, so cross-site requests arrive unauthenticated — no CSRF token needed.

Spring WebFlux & Reactive

Spring WebFlux provides a non-blocking, reactive web stack based on Project Reactor. It shines for high-concurrency I/O — proxying, streaming, and real-time use cases — but has a steeper learning curve.

Reactive Types

TypeDescriptionAnalogy
Mono<T>0 or 1 elementCompletableFuture / Optional

Reactive Controller & Service

// WebFlux controller — returns reactive types
@RestController
@RequestMapping("/api/v1/users")
public class ReactiveUserController {
    private final UserService userService;

    @GetMapping("/{id}")
    public Mono<ResponseEntity<UserResponse>> getUser(@PathVariable Long id) {
        return userService.findById(id)
            .map(ResponseEntity::ok)
            .defaultIfEmpty(ResponseEntity.notFound().build());
    }

    // Server-Sent Events — stream live updates
    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<UserEvent> streamUsers() {
        return userService.getUserEventStream();
    }
}

// Reactive pipeline — compose operators, never block
public Mono<OrderResponse> placeOrder(OrderRequest req) {
    return userService.findById(req.getUserId())      // Mono
        .switchIfEmpty(Mono.error(new NotFoundException()))
        .flatMap(user -> inventoryService.reserve(req))  // async, returns Mono
        .flatMap(reserved -> paymentService.charge(req))
        .map(payment -> new OrderResponse(payment))
        .onErrorResume(PaymentException.class,
            e -> inventoryService.release(req).then(Mono.error(e)));  // compensate
}

MVC vs WebFlux

Spring MVC Spring WebFlux Thread-per-request Event loop (Netty or Reactor Netty) Blocking I/O OK Non-blocking I/O required Simpler mental model Back-pressure, reactive streams Good for: CRUD APIs Good for: streaming, high-concurrency Max ~200 concurrent req/thread 100k+ concurrent connections NEVER mix blocking code into WebFlux — it stalls the event loop!
Blocking in Reactive

Q: What is the key difference between map() and flatMap() on a Mono?

A) map() is faster
B) flatMap() only works with Flux
C) map() transforms the value synchronously (T → R). flatMap() transforms to another reactive type (T → Mono<R>) and flattens it — use flatMap() when the transformation itself is async (e.g., a DB call)
D) They are interchangeable
✓ Correct! map() is for synchronous transformations; flatMap() is for async ones. Using map() to return a Mono gives you a Mono<Mono<T>> — you almost always want flatMap() for chaining async operations.

Q: What is a consumer group in Kafka and what does it guarantee?

A) A group of producers writing to the same topic
B) A set of consumer instances sharing a group-id. Kafka guarantees each partition is consumed by exactly one instance in the group — enabling load-balanced parallel processing and horizontal scaling
C) A Kafka security concept for access control
D) A batch of messages processed atomically
✓ Correct! Consumer groups are Kafka's horizontal scaling mechanism. To increase throughput, add more instances (up to the number of partitions). Different consumer groups receive their own copy of every message — useful for fan-out to multiple services.

// Service — cache, evict, update
@Service
public class UserService {

    @Cacheable(value = "users", key = "#id")  // cache-aside: check before call
    public UserResponse findById(Long id) {
        return userRepository.findById(id).map(mapper::toResponse)
            .orElseThrow(() -> new NotFoundException(id));
    }

    @CachePut(value = "users", key = "#result.id")  // update cache on write
    public UserResponse update(Long id, UpdateUserRequest req) {
        return mapper.toResponse(userRepository.save(mapper.update(req)));
    }

    @CacheEvict(value = "users", key = "#id")    // evict on delete
    public void delete(Long id) {
        userRepository.deleteById(id);
    }
}

Distributed Lock with Redis

// Atomic lock: SET key value NX PX ttl
public boolean tryLock(String key, String value, Duration ttl) {
    Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent(key, value, ttl);
    return Boolean.TRUE.equals(acquired);
}

// Use Redisson for production-grade distributed locking
RLock lock = redissonClient.getLock("order-lock:" + orderId);
try {
    if (lock.tryLock(5, 30, TimeUnit.SECONDS)) {
        processOrder(orderId);
    }
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
Cache Stampede
When a cached key expires and many threads miss simultaneously, all hit the DB at once. Fix: use probabilistic early expiration, a "lock-and-refresh" pattern (Redisson), or set different TTLs per region using RedisCacheManager.withInitialCacheConfigurations().

Q: What is the difference between @Cacheable and @CachePut?

A) They are identical — both check then populate the cache
B) @CachePut deletes the cache entry
C) @Cacheable skips the method body if the cache has a hit. @CachePut always executes the method and updates the cache with the result — use it on write methods to keep the cache consistent
D) @Cacheable works only with Redis, @CachePut works with any provider
✓ Correct! Using @CachePut on update/create methods ensures that reads after a write always hit the cache with fresh data — avoiding the stale-read window that exists with evict-and-reload patterns.

Multi-Instance Scheduling
In a multi-instance deployment, @Scheduled runs on every instance simultaneously. Use ShedLock or spring-integration-jdbc (distributed lock via DB) to ensure a job runs on only one instance at a time.

Q: What is the difference between fixedRate and fixedDelay in @Scheduled?

A) They are the same — both wait for the previous execution
B) fixedRate uses cron syntax
C) fixedRate fires every N ms from the start of the previous invocation (can overlap if execution takes longer). fixedDelay fires N ms after the previous invocation COMPLETES — guarantees no overlapping executions
D) fixedDelay only works with async methods
✓ Correct! For jobs that must not overlap (e.g., DB cleanup), use fixedDelay. For heartbeats and polling that must fire at steady intervals regardless of processing time, use fixedRate — but add a guard if overlapping execution would be harmful.

Outbox Pattern — Reliable Event Publishing

// Problem: service crashes between DB commit and Kafka publish
// Solution: write events to outbox table in SAME transaction as domain data

@Transactional
public Order placeOrder(OrderRequest req) {
    Order order = orderRepository.save(new Order(req));

    // Write to outbox in same TX — atomically with the order
    outboxRepository.save(new OutboxEvent(
        UUID.randomUUID().toString(),
        "order-events",
        objectMapper.writeValueAsString(order)
    ));
    return order;
}

// Separate process (Debezium CDC or scheduled poller) reads outbox and publishes
// @Scheduled(fixedDelay = 1000)

Choreography vs Orchestration
Choreography: services react to events autonomously — no central coordinator, better autonomy, harder to trace. Orchestration: a saga orchestrator tells services what to do — easier to observe, central failure point. For complex sagas with compensations, orchestration (Temporal, Axon) is more maintainable.

Q: What problem does the Outbox Pattern solve in microservices?

A) It prevents duplicate messages in Kafka
B) It reduces Kafka partition count
C) It solves the dual-write problem — writing to the DB and publishing an event are made atomic by using a DB outbox table, so a crash can't cause the event to be lost (the outbox is processed by a separate reliable process)
D) It improves read performance with CQRS
✓ Correct! Without the outbox, a service crash between db.save() and kafka.send() creates data inconsistency. The outbox pattern makes them atomic at the DB level — the CDC/poller guarantees at-least-once delivery from there.

@Component
public class CorrelationIdFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String correlationId = exchange.getRequest().getHeaders()
            .getFirst("X-Correlation-ID");
        if (correlationId == null) {
            correlationId = UUID.randomUUID().toString();
        }
        ServerWebExchange mutated = exchange.mutate()
            .request(r -> r.header("X-Correlation-ID", correlationId))
            .build();
        return chain.filter(mutated);
    }

    @Override
    public int getOrder() { return -1; }
}

C) The lb:// scheme tells Spring Cloud LoadBalancer to resolve the logical service name against the service registry (Eureka, Consul, or Kubernetes DNS) and pick an instance using round-robin or weighted load balancing
D) It creates a local in-memory proxy
✓ Correct! lb:// delegates to ReactiveLoadBalancerClientFilter which calls the ReactiveLoadBalancer — by default Spring Cloud LoadBalancer (replaced Ribbon). No hardcoded host:port needed.

Circuit Breaker & Resilience4j

Resilience4j is the Spring-recommended fault tolerance library, replacing Netflix Hystrix. It provides circuit breakers, retry, rate limiting, bulkhead, and time limiting — composable via annotations or functional API.

Circuit Breaker States

CLOSED ──(failure rate > threshold)──▶ OPEN ▲ │ │ (wait duration) │ ▼ HALF_OPEN ◀──────────────────────── OPEN │ ├─(probe calls succeed)──▶ CLOSED └─(probe calls fail)────▶ OPEN

Resilience4j Configuration

# application.yml
resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        slidingWindowSize: 10
        failureRateThreshold: 50        # open if 50%+ fail
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3
        recordExceptions:
          - org.springframework.web.client.HttpServerErrorException
          - java.io.IOException
  retry:
    instances:
      paymentService:
        maxAttempts: 3
        waitDuration: 500ms
        exponentialBackoffMultiplier: 2  # 500ms → 1s → 2s
  bulkhead:
    instances:
      paymentService:
        maxConcurrentCalls: 10          # limit concurrent calls
// Annotation-based — CB wraps the method, fallback on open/error
@Service
public class PaymentService {

    @CircuitBreaker(name = "paymentService", fallbackMethod = "fallbackCharge")
    @Retry(name = "paymentService")
    @Bulkhead(name = "paymentService")
    public PaymentResult charge(PaymentRequest request) {
        return paymentGateway.process(request);
    }

    private PaymentResult fallbackCharge(PaymentRequest request, Exception ex) {
        log.warn("Payment circuit open, using fallback", ex);
        return PaymentResult.pending(request.getOrderId());  // queue for retry
    }
}

Q: When should the circuit breaker be in HALF_OPEN state?

A) When 50% of calls fail
B) After the configured waitDurationInOpenState elapses from the OPEN state — a limited number of probe calls are allowed through to test if the downstream service has recovered, before transitioning back to CLOSED or returning to OPEN
C) When the service restarts
D) When CPU usage drops below 50%
✓ Correct! HALF_OPEN is the recovery probe state. It prevents the circuit from staying open forever — periodically testing if the downstream dependency has healed without flooding it with traffic.

Graceful Shutdown
Enable Spring Boot's built-in graceful shutdown: server.shutdown=graceful and spring.lifecycle.timeout-per-shutdown-phase=30s. Kubernetes sends SIGTERM, then waits terminationGracePeriodSeconds before SIGKILL — set it to 60s to give the JVM time to drain.

Q: Why use -XX:+UseContainerSupport and -XX:MaxRAMPercentage in containers?

A) They enable Docker networking
B) They disable garbage collection in containers
C) Without UseContainerSupport, the JVM reads the host's total RAM instead of the container's memory limit — leading to OOM kills. MaxRAMPercentage=75 sizes the heap relative to the container limit, leaving headroom for off-heap (Metaspace, threads, NIO)
D) They speed up JVM startup time
✓ Correct! This is a critical production JVM flag. JDK 11+ includes UseContainerSupport by default but it's good practice to be explicit. Set MaxRAMPercentage=75 to keep ~25% for non-heap memory and avoid OOM kills under load.

Q: Why should you set -XX:+ExitOnOutOfMemoryError in containerised Spring Boot apps?

A) It prevents the OOM from occurring
B) It writes the heap dump before crashing
C) After an OOM, the JVM is in an undefined state and may continue running with corrupted data or deadlocked threads. Crashing immediately lets Kubernetes restart the pod cleanly — a known-good state is safer than a zombie process
D) It is required by Kubernetes health probes
✓ Correct! Fail-fast is a core production principle. Combine with HeapDumpOnOutOfMemoryError (dump before exit) and a persistent volume for the dump file — so you can analyse the OOM cause post-incident without keeping the zombie alive.

Q: A Spring Boot app returns JPA entity objects directly from REST controllers. What are the risks?

A) Jackson can't serialize JPA entities
B) Entities are always immutable so the response may be stale
C) Multiple risks: (1) LazyInitializationException if lazy collections are accessed during serialization outside a transaction, (2) infinite loops from bidirectional relationships, (3) exposes internal schema to API consumers making versioning difficult, (4) unintended data leakage
D) Only a performance concern, not a correctness issue
✓ Correct! Always use DTOs. The mapping overhead is trivial; the benefits — decoupled API and persistence models, no lazy-load surprises, clean versioning — are enormous. Use MapStruct for zero-overhead compile-time mapping in large codebases.
