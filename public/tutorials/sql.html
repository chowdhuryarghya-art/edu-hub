Module 1

Relational Model & Database Architecture

Understand relations, tuples, attributes, domain integrity, and primary vs foreign key constraints.

🎯 Real-World Problem Scenario

University Student Enrollment & Department Mapping

A university administration needs to store student records and assign them to academic departments. The system must strictly ensure: (1) No duplicate students exist, (2) No student can be enrolled in a non-existent department, and (3) Student GPA grades are strictly bounded between 0.0 and 100.0.

1. Theory & Architectural Concepts

A Relational Database Management System (RDBMS) organizes information into structured two-dimensional tables called Relations. In formal relational theory:

  • Relation (Table): A set of unordered tuples sharing the exact column definitions.
  • Tuple (Row / Record): A single entity instance containing concrete attribute values.
  • Attribute (Column / Field): A named property with an enforced data type and domain constraint.
  • Degree: The total number of columns in a table.
  • Cardinality: The total number of rows in a table.
The Three Fundamental Integrity Rules
  • Entity Integrity: Every table must have a Primary Key; primary key columns cannot contain NULL and must be unique.
  • Referential Integrity: A Foreign Key value in a child table must match an existing Primary Key in the parent table or be explicitly set to NULL.
  • Domain Integrity: Every column entry must be valid according to its defined type and range constraints (e.g. grade FLOAT CHECK (grade >= 0.0 AND grade <= 100.0)).

2. Production SQL Solution

-- Parent Table: Academic Departments
CREATE TABLE departments (
    dept_id INT PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL UNIQUE,
    building VARCHAR(50) NOT NULL,
    budget INT CHECK (budget > 0)
);

-- Child Table: Students with Referential & Domain Integrity Constraints
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    grade DECIMAL(4, 2) CHECK (grade >= 0.0 AND grade <= 100.0),
    city VARCHAR(50) DEFAULT 'Undisclosed',
    dept_id INT,
    CONSTRAINT fk_student_dept FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
        ON UPDATE CASCADE 
        ON DELETE SET NULL
);

-- Seed Data
INSERT INTO departments VALUES (1, 'Computer Science', 'Turing Hall', 750000);
INSERT INTO departments VALUES (2, 'Information Tech', 'Babbage Hall', 620000);

INSERT INTO students VALUES (101, 'Alice Chen', 94.50, 'New York', 1);
INSERT INTO students VALUES (102, 'Bob Sharma', 82.00, 'Mumbai', 2);
⚠️ Common Pitfall: Orphaned Foreign Keys

Inserting a row with dept_id = 99 when department 99 does not exist triggers an immediate FOREIGN KEY constraint failed exception. Always ensure parent records exist prior to child insertion.

💡 Concept Q&A / Knowledge Check
Q1: What happens on DELETE if ON DELETE SET NULL is specified on a Foreign Key? ▼
Answer: When a department record is deleted from departments, the database automatically sets the corresponding dept_id in the students table to NULL instead of deleting the student or failing the delete operation.
Q2: What is the difference between Candidate Key, Primary Key, and Alternate Key? ▼
Answer: A Candidate Key is any minimal set of attributes that can uniquely identify a tuple. The Primary Key is the candidate key chosen by the database architect. All remaining candidate keys that were not chosen are Alternate Keys.
Module 2

DDL Commands & Schema Constraints

Master CREATE, ALTER, DROP, TRUNCATE, and table constraint mechanisms.

🎯 Real-World Problem Scenario

E-Commerce Product Inventory Schema Migration

An e-commerce business launched with a basic products table. Three months later, they need to add a mandatory sku_code (which must be unique and exactly 8 alphanumeric characters), add a non-negative stock_quantity, and rename the legacy cost column to retail_price without dropping existing sales data.

1. Theory: DDL Operations

Data Definition Language (DDL) statements define and modify the structural blueprint of the database. DDL statements are auto-committed in standard relational engines.

  • CREATE TABLE: Allocates metadata structure and column types.
  • ALTER TABLE: Adds, alters, renames, or drops columns and constraints on existing tables.
  • DROP TABLE: Permanently destroys table metadata, indexes, and all stored tuples.
  • TRUNCATE TABLE: Fast deallocation of all table data pages while keeping table structure intact.

2. Production SQL Solution

-- Initial Base Table
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(120) NOT NULL,
    cost DECIMAL(10, 2) NOT NULL
);

-- Schema Migration Step 1: Add SKU column with UNIQUE constraint
ALTER TABLE products ADD COLUMN sku_code VARCHAR(8) UNIQUE;

-- Schema Migration Step 2: Add Inventory column with non-negative validation
ALTER TABLE products ADD COLUMN stock_quantity INT DEFAULT 0 CHECK (stock_quantity >= 0);

-- Schema Migration Step 3: Rename column for domain clarity
ALTER TABLE products RENAME COLUMN cost TO retail_price;
-- Verified Table Schema: -- products (product_id INT PK, product_name VARCHAR(120), retail_price DECIMAL(10,2), sku_code VARCHAR(8) UNIQUE, stock_quantity INT CHECK(>=0))
💡 Concept Q&A / Knowledge Check
Q1: What is the core architectural difference between DELETE and TRUNCATE? ▼
Answer: DELETE is a DML command that scans and deletes rows individually, firing triggers and logging each row delete in the transaction log (WAL). TRUNCATE is a DDL command that deallocates entire data storage pages in bulk, does not fire row triggers, resets auto-increment sequences, and executes orders of magnitude faster.
Module 3

DML: Insert, Update, Delete & Bulk Operations

Safe data mutations, conditional bulk updates, and cascading operations.

🎯 Real-World Problem Scenario

Annual Corporate Salary Revisions & Employee Offboarding

The HR and Payroll department needs to: (1) Insert new hires in bulk, (2) Apply a 12% salary raise to all employees in the 'Engineering' department who have a current salary below ₹1,00,000, and (3) Safely remove deactivated contractor profiles.

1. Production SQL Solution

-- 1. Bulk Insertion
INSERT INTO employees (emp_id, emp_name, salary, dept_id, role) VALUES
    (201, 'Karan Malhotra', 85000, 1, 'Software Engineer'),
    (202, 'Sara Connor', 92000, 1, 'QA Automation Lead'),
    (203, 'Vikram Seth', 115000, 2, 'DevOps Architect');

-- 2. Conditional Update with Mathematical Transformation
UPDATE employees 
SET salary = ROUND(salary * 1.12, 0)
WHERE dept_id = 1 AND salary < 100000;

-- 3. Targeted Safe Deletion with WHERE clause
DELETE FROM employees 
WHERE role = 'Contractor' AND dept_id IS NULL;
⚠️ Critical Production Gotcha: Unconstrained UPDATE / DELETE

Never run UPDATE employees SET salary = 100000 or DELETE FROM employees without a WHERE clause in production. Doing so modifies or deletes every record in the entire table.

Module 4

Filtering, Pattern Matching & NULL Value Handling

Master Three-Valued Logic (3VL), NULL pitfalls, and LIKE / BETWEEN operators.

🎯 Real-World Problem Scenario

Customer Search & Missing Profile Attribute Detection

A customer relationship portal needs to search for users based in cities starting with 'San' or 'New', who scored above 80% or who have not yet been assigned a mentor (mentor_id IS NULL).

1. Theory: Three-Valued Logic (3VL)

In relational databases, NULL represents the absence of a value (Unknown). Any direct equality comparison like salary = NULL or salary != NULL returns UNKNOWN (which evaluates to False in a WHERE filter).

2. Production SQL Solution

-- Correct query handling NULLs and regex-style wildcard patterns
SELECT student_id, name, city, grade, dept_id
FROM students
WHERE (city LIKE 'New%' OR city LIKE 'San%')
  AND (grade BETWEEN 80.0 AND 95.0)
  OR dept_id IS NULL
ORDER BY grade DESC;

-- Safe NULL substitution in projection using COALESCE
SELECT 
    name, 
    COALESCE(city, 'City Not Specified') AS display_city,
    COALESCE(dept_id, 0) AS safe_dept_id
FROM students;
💡 Concept Q&A / Knowledge Check
Q: Why does `SELECT * FROM students WHERE grade = NULL;` return 0 rows? ▼
Answer: In SQL Three-Valued Logic, comparing any value to NULL yields UNKNOWN, never TRUE. To test for missing data, SQL mandates using IS NULL or IS NOT NULL.
Module 5

Multi-Table JOINs: INNER, LEFT, RIGHT & FULL

Venn diagram mechanics, relational Cartesian products, and multi-entity joins.

🎯 Real-World Problem Scenario

Departmental Course Enrollment & Unassigned Student Audit

Generate a comprehensive academic report displaying: (1) All enrolled students and their department details, and (2) Departments that currently have zero students registered so the dean can allocate marketing resources.

1. Production SQL Solution

-- 1. INNER JOIN: Returns only matching rows between both tables
SELECT s.student_id, s.name, s.grade, d.dept_name, d.building
FROM students s
INNER JOIN departments d ON s.dept_id = d.dept_id;

-- 2. LEFT OUTER JOIN: Returns ALL departments, even if no students are assigned
SELECT d.dept_name, d.building, COUNT(s.student_id) AS enrolled_students
FROM departments d
LEFT JOIN students s ON d.dept_id = s.dept_id
GROUP BY d.dept_id, d.dept_name, d.building
ORDER BY enrolled_students ASC;

Module 6

Self Joins, Cross Joins & Hierarchical Trees

Representing employee-manager hierarchies and Cartesian combinations.

🎯 Real-World Problem Scenario

Corporate Organizational Chart & Direct Manager Lookup

Every employee record contains a manager_id pointing to another employee's emp_id in the same table. Generate a report showing every employee's name alongside their direct reporting manager's name.

1. Production SQL Solution

-- Self Join with Aliasing
SELECT 
    e.emp_name AS employee_name,
    e.role     AS employee_role,
    COALESCE(m.emp_name, 'Executive Board / CEO') AS manager_name
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id
ORDER BY e.dept_id, e.salary DESC;
Module 7

GROUP BY, HAVING & Aggregate Functions

Statistical aggregations, logical execution ordering, and group filtering.

🎯 Real-World Problem Scenario

High-Value Department Payroll & Bonus Eligibility

Identify all departments with at least 2 active staff members where the average employee salary exceeds ₹80,000. Display the total salary expenditure, average salary, and top individual earner in that department.

⚠️ Common Pitfall: Filtering Aggregates in WHERE

Writing WHERE AVG(salary) > 80000 produces an immediate SQL syntax error! WHERE executes before grouping occurs. Aggregates can only be filtered in the HAVING clause.

1. Production SQL Solution

-- Grouping with multiple aggregate metrics and HAVING filter
SELECT 
    d.dept_name,
    COUNT(e.emp_id)               AS total_employees,
    SUM(e.salary)                 AS total_payroll,
    ROUND(AVG(e.salary), 2)       AS avg_salary,
    MAX(e.salary)                 AS highest_salary
FROM departments d
INNER JOIN employees e ON d.dept_id = e.dept_id
GROUP BY d.dept_id, d.dept_name
HAVING COUNT(e.emp_id) >= 2 AND AVG(e.salary) > 80000
ORDER BY avg_salary DESC;
Logical SQL Query Execution Order
  1. FROM & JOIN (Row sources established)
  2. WHERE (Individual row filtering)
  3. GROUP BY (Cluster rows into buckets)
  4. HAVING (Filter bucket aggregates)
  5. SELECT (Expressions, aliases, and math computed)
  6. ORDER BY (Sort final recordset)
  7. LIMIT / OFFSET (Pagination)
Module 8

Subqueries: Scalar, Correlated & EXISTS

Nested queries, EXISTS vs IN performance benchmarks, and row-by-row correlation.

🎯 Real-World Problem Scenario

Employees Earning Above Their Department Average

Find all employees whose individual salary is strictly greater than the average salary of their own specific department.

1. Production SQL Solution (Correlated Subquery)

-- Correlated Subquery: Outer row passes dept_id to inner query
SELECT e.emp_id, e.emp_name, e.salary, e.dept_id
FROM employees e
WHERE e.salary > (
    SELECT AVG(sub.salary)
    FROM employees sub
    WHERE sub.dept_id = e.dept_id
)
ORDER BY e.dept_id, e.salary DESC;
Module 9

Common Table Expressions (CTEs) & Recursive Queries

Modular query structure with WITH clauses and hierarchical tree traversals.

🎯 Real-World Problem Scenario

Multi-Tier Department Budget vs Actual Expense Variance

Compute department payroll stats, calculate variance against the allocated department budget, and classify departments as 'Within Budget' or 'Over Budget'.

1. Production SQL Solution

WITH DeptStats AS (
    SELECT 
        dept_id,
        COUNT(emp_id) AS staff_count,
        SUM(salary)   AS total_spent
    FROM employees
    GROUP BY dept_id
),
DeptAnalysis AS (
    SELECT 
        d.dept_name,
        d.budget,
        COALESCE(s.staff_count, 0) AS staff_count,
        COALESCE(s.total_spent, 0) AS total_spent,
        (d.budget - COALESCE(s.total_spent, 0)) AS remaining_budget
    FROM departments d
    LEFT JOIN DeptStats s ON d.dept_id = s.dept_id
)
SELECT 
    dept_name,
    budget,
    total_spent,
    remaining_budget,
    CASE 
        WHEN remaining_budget < 0 THEN '⚠️ Over Budget'
        WHEN remaining_budget < 100000 THEN '🟡 Near Limit'
        ELSE '🟢 Healthy'
    END AS budget_status
FROM DeptAnalysis
ORDER BY remaining_budget ASC;
Module 10

Window Functions: ROW_NUMBER, RANK & DENSE_RANK

Compute rolling aggregates, leaderboards, and partition-level rankings.

🎯 Real-World Problem Scenario

Top 2 Highest Paid Employees Per Department

Select the top 2 highest-earning employees in every department without losing other column attributes.

1. Production SQL Solution

WITH RankedEmployees AS (
    SELECT 
        emp_id,
        emp_name,
        salary,
        dept_id,
        DENSE_RANK() OVER (
            PARTITION BY dept_id 
            ORDER BY salary DESC
        ) AS salary_rank
    FROM employees
)
SELECT emp_id, emp_name, salary, dept_id, salary_rank
FROM RankedEmployees
WHERE salary_rank <= 2
ORDER BY dept_id, salary_rank;
Module 11

Database Normalization: 1NF, 2NF, 3NF & BCNF

Eliminate insert, update, and delete anomalies through mathematical decomposition.

🎯 Real-World Problem Scenario

De-duplicating a Flawed Denormalized Orders Spreadsheet

An un-normalized orders table contains (order_id, customer_name, customer_city, item_name, item_price, quantity). Updating a customer's city requires updating thousands of rows. Decomposing this table into 3NF eliminates all anomalies.

1. Theory: Normal Forms Breakdown

  • 1NF (First Normal Form): All column values must be atomic (no arrays or comma-separated lists), and each record must have a unique identifier.
  • 2NF (Second Normal Form): Must be in 1NF, and no non-prime attribute may depend on a subset of a composite primary key (No partial dependency).
  • 3NF (Third Normal Form): Must be in 2NF, and no non-prime attribute may depend on another non-prime attribute ($A \rightarrow B \rightarrow C$, No transitive dependency).
  • BCNF (Boyce-Codd Normal Form): For every functional dependency $X \rightarrow Y$, $X$ must be a super key.

Database Indexing, ACID Properties & Transactions

B-Tree indexing, execution plan analysis (EXPLAIN), and transaction isolation levels.

🎯 Real-World Problem Scenario

Double-Entry Financial Funds Transfer

Transfer ₹50,000 from Account A to Account B. If the server loses power or a database trigger fails halfway through, the system must guarantee that Account A is not debited without Account B being credited.

1. Production SQL Solution (ACID Transaction)

-- 1. Accelerate query lookups via Composite B-Tree Index
CREATE INDEX idx_student_dept_grade ON students(dept_id, grade);

-- 2. Atomic Multi-Statement Financial Transaction
START TRANSACTION;

-- Deduct from Source Account
UPDATE bank_accounts 
SET balance = balance - 50000 
WHERE account_id = 'ACC-101' AND balance >= 50000;

-- Credit to Destination Account
UPDATE bank_accounts 
SET balance = balance + 50000 
WHERE account_id = 'ACC-202';

-- Permanently persist both operations together
COMMIT;
