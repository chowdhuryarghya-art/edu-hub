Module 1

Relational Model & Database Architecture

Understand relations, tuples, attributes, domain constraints, and primary vs foreign keys.

1. Theory & Architectural Concepts

A Relational Database Management System (RDBMS) organizes information into structured two-dimensional tables called Relations. In formal relational theory (introduced by E.F. Codd):

  • Relation (Table): A set of unordered rows sharing the same column definitions.
  • Tuple (Row / Record): A single entity instance containing concrete attribute values.
  • Attribute (Column / Field): A named property with an enforced data type and domain constraint.
  • Degree: The total number of columns in a table.
  • Cardinality: The total number of rows in a table.
The Three Fundamental Integrity Rules
  • Entity Integrity: Every table must have a Primary Key; primary key columns cannot contain NULL and must be unique.
  • Referential Integrity: A Foreign Key value in a child table must match an existing Primary Key in the parent table or be explicitly set to NULL.
  • Domain Integrity: Every column entry must be valid according to its defined type and range constraints (e.g. age INT CHECK (age >= 0)).

2. Implementation Example

-- Relational Schema: Departments (Parent) and Students (Child)
CREATE TABLE departments (
    dept_id INT PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    grade DECIMAL(4, 2) CHECK (grade >= 0.0 AND grade <= 100.0),
    dept_id INT,
    CONSTRAINT fk_student_dept FOREIGN KEY (dept_id) REFERENCES departments(dept_id)
);
💡 Concept Q&A / Knowledge Check
Q1: What happens if you try to insert a student with a dept_id that does not exist in departments? ▼
Answer: The RDBMS rejects the query with a Foreign Key / Referential Integrity Violation. This protects the database from having "orphaned records" pointing to non-existent departments.
Q2: What is the difference between a Candidate Key, Primary Key, and Alternate Key? ▼
Answer:
  • Candidate Key: Any minimal column or combination of columns that uniquely identifies each row.
  • Primary Key: The specific candidate key chosen by the database architect as the main identifier.
  • Alternate Key: All remaining candidate keys that were not chosen as the Primary Key (often assigned a UNIQUE constraint).
Module 2

Data Definition Language (DDL) Commands & Constraints

Creating, altering, truncating, and dropping database objects with strict schema constraints.

1. Theory & Mechanics

DDL statements manage the structure/schema of database objects rather than the data records themselves. DDL operations are implicitly committed in most relational engines (such as MySQL/Oracle) and cannot be rolled back.

DDL CommandOperationBehavior
CREATE TABLEBuild new schemaAllocates table metadata and creates column definitions.
ALTER TABLEModify schemaAdds, modifies, or drops columns and constraint definitions.
DROP TABLEDestroy tableDeletes both data records and the entire table schema definition permanently.
TRUNCATE TABLEFast purgeDeletes all rows by deallocating data pages; resets auto-increment counters. Faster than DELETE.

2. Code Example

-- 1. Create table with complete constraints
CREATE TABLE courses (
    course_id VARCHAR(10) PRIMARY KEY,
    course_name VARCHAR(100) NOT NULL,
    credits INT DEFAULT 3 CHECK (credits BETWEEN 1 AND 6),
    dept_id INT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (dept_id) REFERENCES departments(dept_id) ON DELETE CASCADE
);

-- 2. Alter existing schema: Add a new column and index
ALTER TABLE courses ADD COLUMN syllabus_url VARCHAR(255);
ALTER TABLE courses MODIFY COLUMN course_name VARCHAR(150);
💡 Concept Q&A / Knowledge Check
Q1: What is the crucial difference between DROP, TRUNCATE, and DELETE? ▼
Answer:
  • DELETE (DML): Deletes specific rows row-by-row; can be rolled back inside a transaction; triggers fire; does not reset auto-increment.
  • TRUNCATE (DDL): Deallocates all data pages in one operation; resets auto-increment; cannot be rolled back in MySQL; retains table structure.
  • DROP (DDL): Completely destroys both data and table structure definition from the data dictionary.
Module 3

Data Manipulation Language (DML): Insert, Update, Delete

CRUD operations, bulk insertion, safe conditional updates, and transactional row mutations.

1. Theory & Concepts

DML manages data records stored inside tables. Unlike DDL, DML statements operate inside transactions and can be explicitly committed or rolled back using COMMIT and ROLLBACK.

2. Code Example

-- 1. Bulk Insertion
INSERT INTO students (student_id, name, grade, dept_id) VALUES
    (101, 'Aarav Mehta', 92.5, 1),
    (102, 'Diya Sen', 88.0, 2),
    (103, 'Kabir Khan', 74.5, 1);

-- 2. Safe Conditional Update with WHERE clause
UPDATE students
SET grade = grade + 2.0
WHERE dept_id = 1 AND grade <= 90.0;

-- 3. Targeted Deletion
DELETE FROM students
WHERE grade < 40.0;
💡 Concept Q&A / Knowledge Check
Q1: Why is executing UPDATE or DELETE without a WHERE clause extremely dangerous? ▼
Answer: An UPDATE or DELETE statement without a WHERE clause will apply to every single row in the table, potentially corrupting or erasing all production records. Modern SQL clients (like MySQL Workbench) enable "Safe Update Mode" (sql_safe_updates = 1) to reject such queries by default.
Module 4

Query Filtering, Pattern Matching & NULL Handling

Master WHERE conditions, IN, BETWEEN, LIKE wildcards, and Three-Valued Logic with IS NULL.

1. Theory: SQL Three-Valued Logic (3VL)

In SQL, NULL represents missing or unknown information. As a result, comparisons with NULL evaluate to UNKNOWN rather than TRUE or FALSE:

  • NULL = NULL evaluates to UNKNOWN (not TRUE!).
  • To test for null values, you must always use IS NULL or IS NOT NULL.
  • Use COALESCE(col, fallback) to supply a default value when a column contains NULL.

2. Code Example

-- Filtering with IN, BETWEEN, and Wildcard Pattern Matching
SELECT name, grade, city
FROM students
WHERE (grade BETWEEN 80.0 AND 95.0)
  AND city IN ('New York', 'Mumbai', 'Toronto')
  AND name LIKE 'A%'              -- Names starting with 'A'
  AND scholarship_amt IS NOT NULL; -- Correct NULL check
💡 Concept Q&A / Knowledge Check
Q1: What is the difference between '%' and '_' wildcards in the LIKE operator? ▼
Answer:
  • % matches zero or more characters (e.g. 'S%' matches 'Sam', 'Steve', 'S').
  • _ matches exactly one single character (e.g. 'B_b' matches 'Bob', 'Bib', but NOT 'Blob').
Module 5

Multi-Table Relational JOINs (Inner & Outer)

INNER JOIN, LEFT JOIN, RIGHT JOIN, and FULL OUTER JOIN with Venn diagram mechanics.

1. Theory: The JOIN Family

  • INNER JOIN: Returns rows when there is a match in both tables.
  • LEFT (OUTER) JOIN: Returns all rows from the left table, plus matched rows from the right table (unmatched right columns fill with NULL).
  • RIGHT (OUTER) JOIN: Returns all rows from the right table, plus matched rows from the left table.
  • FULL OUTER JOIN: Returns rows when there is a match in either table.

2. Code Example

-- Find all students and their department names (including students with no department)
SELECT 
    s.student_id, 
    s.name AS student_name, 
    COALESCE(d.dept_name, 'Undeclared') AS department
FROM students s
LEFT JOIN departments d ON s.dept_id = d.dept_id
ORDER BY s.student_id;
💡 Concept Q&A / Knowledge Check
Q1: How do you find records in Table A that have NO corresponding match in Table B using a LEFT JOIN? ▼
Answer: Perform a LEFT JOIN from Table A to Table B on the foreign key, and add a WHERE B.primary_key IS NULL clause (known as an Anti-Join pattern).
Module 6

Self Joins, Cross Joins & Hierarchical Queries

Joining a table to itself using aliases for employee-manager hierarchies and Cartesian products.

1. Theory & Concepts

A Self Join is a regular join where a table is joined with itself. It is the classic pattern for querying hierarchical and parent-child tree data structures stored in a single table (e.g. employee reporting to manager).

2. Code Example

-- Employee and Manager Hierarchy Query via Self Join
SELECT 
    e.emp_name AS employee,
    e.role AS employee_role,
    COALESCE(m.emp_name, 'Top Level Executive') AS manager_name
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;
💡 Concept Q&A / Knowledge Check
Q1: What is a CROSS JOIN and what is its output cardinality? ▼
Answer: A CROSS JOIN produces the Cartesian Product of two tables. If Table A has $M$ rows and Table B has $N$ rows, the CROSS JOIN produces exactly $M \times N$ rows.
Module 7

GROUP BY, HAVING & Aggregate Functions

COUNT, SUM, AVG, MIN, MAX, grouping buckets, and WHERE vs HAVING filtering order.

1. Theory: Query Execution Order

Understanding the internal order in which SQL executes clauses is critical for writing correct aggregates:

1. FROM & JOINs    (identifies working table dataset)
2. WHERE           (filters raw rows BEFORE grouping)
3. GROUP BY        (collapses rows into aggregate buckets)
4. HAVING          (filters grouped buckets AFTER aggregation)
5. SELECT          (computes projections and aliases)
6. DISTINCT        (removes duplicate result rows)
7. ORDER BY        (sorts final output)
8. LIMIT / OFFSET  (paginates result set)

2. Code Example

-- Find departments with at least 2 students and an average grade above 80
SELECT 
    d.dept_name,
    COUNT(s.student_id) AS total_students,
    ROUND(AVG(s.grade), 2) AS avg_grade
FROM departments d
JOIN students s ON d.dept_id = s.dept_id
WHERE s.grade >= 50.0  -- Filter individual failing rows first
GROUP BY d.dept_name
HAVING COUNT(s.student_id) >= 2 AND AVG(s.grade) > 80.0
ORDER BY avg_grade DESC;
💡 Concept Q&A / Knowledge Check
Q1: Why can't you use WHERE AVG(grade) > 80.0? ▼
Answer: The WHERE clause evaluates row-by-row before any grouping occurs. Aggregate functions (like AVG, COUNT, SUM) operate on grouped sets of rows, which only exist after GROUP BY. Therefore, aggregate filtering must be placed in the HAVING clause.
Module 8

Subqueries & Nested Queries (Scalar & Correlated)

Single-row, multi-row (IN/ANY/ALL), and correlated subqueries with EXISTS and NOT EXISTS.

1. Theory: Scalar vs Correlated Subqueries

  • Independent / Scalar Subquery: Executes once independently; its result is passed to the outer query.
  • Correlated Subquery: References a column from the outer query table ($e.dept\_id = d.dept\_id$). It re-executes for every candidate row in the outer query.

2. Code Example

-- Find students whose grade is above their own department's average grade
SELECT s.name, s.grade, s.dept_id
FROM students s
WHERE s.grade > (
    SELECT AVG(inner_s.grade)
    FROM students inner_s
    WHERE inner_s.dept_id = s.dept_id  -- Correlated reference!
);
💡 Concept Q&A / Knowledge Check
Q1: Why is EXISTS generally faster than IN for checking record existence in large tables? ▼
Answer: EXISTS utilizes short-circuit evaluation: as soon as the query planner finds the first matching row, it immediately returns TRUE without scanning the rest of the subquery table. Additionally, EXISTS handles NULL values safely without unexpected truth-table pitfalls.
Module 9

Common Table Expressions (CTEs) & Recursive Queries

WITH clause syntax, modular query composition, and recursive tree traversal for organizational charts.

1. Theory: Why use CTEs?

A Common Table Expression (CTE) defines a temporary named result set available within the execution scope of a single SELECT, INSERT, UPDATE, or DELETE. CTEs dramatically improve readability over deeply nested subqueries and enable recursion.

2. Code Example

-- CTE to calculate department statistics and filter top departments
WITH DeptStats AS (
    SELECT 
        dept_id,
        COUNT(*) AS student_count,
        AVG(grade) AS avg_dept_grade
    FROM students
    GROUP BY dept_id
),
HighPerformingDepts AS (
    SELECT dept_id 
    FROM DeptStats 
    WHERE avg_dept_grade > 85.0
)
SELECT s.name, s.grade, d.dept_name
FROM students s
JOIN departments d ON s.dept_id = d.dept_id
WHERE s.dept_id IN (SELECT dept_id FROM HighPerformingDepts);
💡 Concept Q&A / Knowledge Check
Q1: What are the two essential components of a RECURSIVE CTE? ▼
Answer: An Anchor Member (initial base query that starts the recursion) combined via UNION ALL with a Recursive Member (a query that references the CTE name and includes an exit termination condition).
Module 10

Window Functions: ROW_NUMBER, RANK, DENSE_RANK & LEAD/LAG

OVER clause, PARTITION BY, ORDER BY frame specifications, and running totals.

1. Theory & Concepts

Unlike GROUP BY (which collapses rows into a single summary row), Window Functions compute calculations across a set of related table rows while retaining individual row identities in the final output.

2. Code Example

-- Ranking students within their respective departments
SELECT 
    name,
    dept_id,
    grade,
    ROW_NUMBER() OVER(PARTITION BY dept_id ORDER BY grade DESC) AS row_num,
    RANK() OVER(PARTITION BY dept_id ORDER BY grade DESC) AS rank_pos,
    DENSE_RANK() OVER(PARTITION BY dept_id ORDER BY grade DESC) AS dense_rank_pos,
    LAG(grade, 1) OVER(PARTITION BY dept_id ORDER BY grade DESC) AS next_higher_grade
FROM students;
💡 Concept Q&A / Knowledge Check
Q1: What is the exact difference between RANK() and DENSE_RANK() when there are ties? ▼
Answer:
  • RANK() leaves gaps in numbering after ties. For tied scores at rank 1, ranks become: 1, 1, 3, 4.
  • DENSE_RANK() does NOT leave gaps. For tied scores at rank 1, ranks become: 1, 1, 2, 3.
Module 11

Database Normalization: 1NF, 2NF, 3NF & BCNF

Eliminating insertion, update, and deletion anomalies through functional dependency decomposition.

1. Theory & Normal Form Progression

Normal FormRequirement & RuleAnomaly Eliminated
1NF (First Normal Form)Atomic values only; no repeating groups or arrays.Multi-valued entry anomalies.
2NF (Second Normal Form)Must be in 1NF + No Partial Dependency (every non-key attribute must depend on the whole composite primary key).Redundancy in composite key tables.
3NF (Third Normal Form)Must be in 2NF + No Transitive Dependency (non-key attributes must not determine other non-key attributes).Transitive update anomalies.
BCNF (Boyce-Codd NF)For every functional dependency $X \rightarrow Y$, $X$ must be a super key.Anomalies where candidate keys overlap.
💡 Concept Q&A / Knowledge Check
Q1: What is a Transitive Dependency? ▼
Answer: An indirect functional dependency where column A determines column B, and column B determines column C ($A \rightarrow B \rightarrow C$). In 3NF, column C must be moved to a separate table where B is the primary key.
Module 12

Database Indexing, ACID Properties & Transactions

B-Tree vs Hash indexes, query execution plans (EXPLAIN), and isolation levels.

1. Theory: The ACID Principles

  • Atomicity: "All or nothing" — all statements in a transaction succeed, or the entire transaction is rolled back.
  • Consistency: The database transitions from one valid state to another, preserving all schema constraints.
  • Isolation: Concurrent transactions execute independently without interfering with one another (Read Committed, Repeatable Read, Serializable).
  • Durability: Once committed, transaction writes survive power losses and crashes via Write-Ahead Logging (WAL).

2. Code Example

-- B-Tree Index Creation & EXPLAIN Query Analysis
CREATE INDEX idx_student_dept_grade ON students(dept_id, grade);

-- Transaction Block Demo
START TRANSACTION;
UPDATE accounts SET balance = balance - 500 WHERE account_id = 101;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 202;
COMMIT; -- Permanently saves changes
💡 Concept Q&A / Knowledge Check
Q1: Why doesn't adding an index on every single column improve performance? ▼
Answer: While indexes accelerate read queries (SELECT), every additional index imposes write overhead during INSERT, UPDATE, and DELETE operations because the RDBMS must rebalance the B-Tree index structures on disk.
